# 中断安全与并发分析（U1 固件）

> 触发来源：`logicprobe_concurrency_scan` 对"该环形缓冲是中断安全的 / 不存在数据竞争"这两条绝对断言标记为 **error（需要专门验证）**。本文给出显式证明与残余风险，替代模糊断言。

---

## 1. 上下文

STM32F103C8T6，单核，**无 RTOS**。只有两个执行上下文会触碰共享数据：

| 上下文 | 入口 | 跑什么 |
|---|---|---|
| USB CDC 中断 | `USB_LP_CAN1_RX0_IRQHandler` / `USB_HP_CAN1_TX_IRQHandler` → `HAL_PCD_IRQHandler` → `USBD_LL_DataOutStage` → `CDC_Receive_FS` → `APP_USB_Receive` → `APP_Frame_Feed` | **只把字节压进环形缓冲** |
| 主循环 | `main` → `APP_Run` → `APP_Frame_Poll` / `APP_HandlePendingFrame` / `FwUpload_TimeoutCheck` / `ISP_Step` | 解析、Flash 读写、ISP、USB 发送 |

设计原则：**中断里只做 O(1) 的搬运，所有解析与业务都在主循环**。

## 2. 共享对象清单（穷举）

| 对象 | 谁写 | 谁读 | 同步手段 |
|---|---|---|---|
| `ring[512]` | 仅 USB 中断（`ring[ring_head]`） | 仅主循环（`ring[ring_tail]`） | SPSC 无锁（见 §3） |
| `ring_head` | 仅 USB 中断 | 仅主循环 | `volatile uint16_t`，单指令读写 |

| `frame_buf` / `frame_pos` / `frame_dlen` / `frame_ready` / `frame_st` | 仅主循环 | 仅主循环 | **不共享**，无需同步 |

## 3. 环形缓冲的显式正确性论证

记 `N = 512`，掩码 `M = N-1`，`H = ring_head`（生产者指针，仅 ISR 写），`T = ring_tail`（消费者指针，仅主循环写）。
所谓"存活区间"是环形区间 `[T, H)`；不变式 **INV：生产者永不写存活区间内的槽位**。

### 3.1 生产者不会覆盖未被读取的槽位

生产者序：`t ← T`（快照）→ `next ← (H+1) & M` → 若 `next == t` 则丢弃；否则 `ring[H] ← byte` → `H ← next`。

- **`T` 只会单调前进**（只由消费者推进，消费者每步把 T 加 1）。因此生产者读到的 `t` 至多是"真实 T 的旧值"，即 `t` 在环序上不超前于 T。
  用旧 `t` 判断"满"只会**更容易判满**（把可用空间算少），方向是保守的 → 最多多丢一个字节，不会误以为有空位。
- **写入的槽位是 `ring[H]`，而消费者读的是 `ring[T]`。** 缓冲区空时 `H == T` 且 `next = (H+1)&M ≠ H`（因 N>1），生产者写 `ring[H]` 而消费者此时不读任何槽；缓冲区非空时 `H ≠ T`，故 `ring[H] ≠ ring[T]`。
  ⇒ 生产者写入的槽位**永远不是**消费者正在读的那一个。∎

### 3.2 消费者不会读到写了一半的数据

- 生产者的可见顺序是 `ring[H] ← byte` **之后**才 `H ← next`。Cortex-M3 单核按程序序对同一核可见，且 `H` 是 `volatile`，编译器不会把两次访问重排。消费者只有在观察到 `H` 前进后才可能取到新字节。∎
- 消费者序：`b ← ring[T]` → `T ← (T+1)&M`。中断可能插在两条指令之间推进 `H`，但不会影响 `ring[T]`（由 3.1 保证），也不会撕裂 `T`（见 3.3）。∎

### 3.3 指针读写不会撕裂

Cortex-M3 上对**自然对齐的 16 位对象**的读写是单条 `LDRH`/`STRH`，中断只能在指令边界插入，不会打断一条指令。故 `H`、`T` 的每次读写都是原子的。`TxState` 是 `uint8_t`，同理。∎

### 3.4 消费者读到"过期的 H"是安全的

主循环读 `H` 时被 USB 中断打断、中断推进了 `H`，则主循环用的是旧 `H`：循环提前结束，本轮少取几个字节，**下一轮 `APP_Frame_Poll()` 会继续取**。方向安全。∎

### 3.5 结论

在上述前提（**恰好一个生产者、恰好一个消费者、各指针单一写者、单核、指针自然对齐且为 volatile**）下，环形缓冲**不需要关中断、不需要互斥锁**，且不会出现覆盖未读数据或读到半写数据的情形。

> ⚠ 该结论**依赖前提**：一旦将来有人把 `APP_Frame_Feed` 从主循环调用（变成两个生产者），或把 `APP_Frame_Poll` 放进中断，本证明立即失效。代码注释与会话记录中已标注"仅 ISR 调用 / 仅主循环调用"。

## 4. 残余风险（**未**被上面的证明覆盖）

| # | 风险 | 影响 | 现状处理 |
|---|---|---|---|
| R1 | `ISP_Step()` 中 `HAL_Delay` 最长阻塞约 15 s（等全片擦除 ACK），期间若 PC 持续发帧，512B 环形缓冲会被填满并**丢弃字节** | 可能留下半截帧，导致后续命令被误解析 | ① 帧层有 CRC 兜底 + `frame_resync()` 重新对齐；② **烧录结束后调用 `APP_Frame_Init()` 清空接收侧**，保证下一条命令从干净状态开始；③ 协议本身要求 PC 等 `0x0112` 的 ACK 才继续 |
| R2 | 缓冲满时丢弃的是**最新**字节（而非最旧） | 丢的是当前帧的尾部 | 属安全降级方向（不覆盖已收数据）；由 R1 的兜底恢复 |
| R3 | USB 未枚举时 `hUsbDeviceFS.pClassData` 为 NULL | 解引用会 HardFault | `APP_WaitTxDone()` 显式判 NULL 返回；且发送只发生在收到帧之后（即枚举之后） |
| R4 | USB 发送忙等上限 50 ms；超时则**放弃发送该 ACK** | PC 收不到 ACK 会超时重试 | FS 下一帧 ≤64B 约 1 ms，50 ms 余量充分；只在主循环上下文忙等，不在 ISR 内 |
| R5 | 中断优先级：USB 与 SysTick 均为默认优先级 | —— | 本节论证不依赖优先级；分析结论仅依赖"单核 + 单写者 + 原子指针读写" |
| R6 | `volatile` 只能阻止编译器重排，不提供内存屏障 | —— | 单核同上下文可见，无需屏障；若将来上 RTOS/双核需重新评估 |
