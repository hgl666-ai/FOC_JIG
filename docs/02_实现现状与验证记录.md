## 2. 协议（从 xlsx 逐格提取）

### 2.1 单帧结构（最低 10 字节）

| 字段 | 帧头 F | 命令 C | 帧序号 N | 数据长度 L | 数据 D | CRC16 |
|---|---|---|---|---|---|---|
| 字节数 | 2 | 2 | 2 | 2 | * | 2 |
| 数据类型 | A5 5B | uint16_t | uint16_t | uint16_t | * | uint16_t |

- **字节序**：所有数据**大端**。
- **帧头**：固定 `0xA5 0x5B`。
- **命令**：从 `0x01` 开始，`0x00` 不使用。
- **帧序号**：从 `0x01` 起递增 u16，`0xFFFF` 后回卷到 1；**序号 0 特殊对待**（治具主动帧用 0）。
  PC 发一帧 → 治具回 ACK，**ACK 序号与收到的序号相同**。
- **数据长度**：u16，表示 D 的字节数。
- **CRC16**：MODBUS/CRC16，**从「帧头 F」到「数据 D」全部参与计算**，CRC 本身大端存放。

### 2.2 命令表

| 功能 | 发送方 | 命令 | 帧序号 | LEN | 数据 D |
|---|---|---|---|---|---|
| 固件 起始帧 | PC | `0x0009` | N | 9 | 2B u16 总帧数 + 4B u32 文件大小 + 3B 版本号 |
| 固件 起始帧 ACK | 治具 | `0x0009` | N | 1 | 1B 错误码 |
| 固件 数据帧 | PC | `0x000A` | N | L | L 字节 OTA 数据 |
| 固件 数据帧 ACK | 治具 | `0x000A` | N | 1 | 1B 错误码 |
| 固件 结束帧 | PC | `0x000B` | N | 0 | / |
| 固件 结束帧 ACK | 治具 | `0x000B` | N | 1 | 1B 状态码 |
| 烧录 Flash 固件到 FOC 板 | PC | `0x0112` | N | 0 | / |
| 烧录 Flash 固件 ACK | 治具 | `0x0112` | N | 1 | 1B 状态码（**烧录完成后才返回**，`00` 成功） |
| 查询固件版本号（Flash 中） | PC | `0x000C` | N | 0 | / |
| 查询固件版本号 ACK | 治具 | `0x000C` | N | 4 | 状态码 + 3B [主][次][修订] |
| 查询固件版本号（FOC 板中） | PC | `0x000D` | N | 0 | / |
| 查询固件版本号 ACK | 治具 | `0x000D` | N | 4 | 状态码 + 3B [主][次][修订]（失败时 `00 FF FF`） |
| **测量** | PC | `0x000E` | N | 1 | mode：`00` 只读最近一批 / `01` 触发一次测试 |
| **测量 ACK（ADC）** | 治具 | `0x000E` | N | 77 | 状态码 + 55B 快照 + 21B 交叉校验块（见 `docs/07` §3；mode=1 时**测试跑完才回**） |
| **脉冲捕获** | PC | `0x000F` | N | 1 | mode：`00` 只读最近一个窗口 / `01` 触发一次 200ms 捕获 |
| **脉冲捕获 ACK** | 治具 | `0x000F` | N | 91 | 状态码 + 45B 本片（输出端）+ 45B 对侧 U2（输入端），见 `docs/12` §6 |

> `0x000E`（ADC 测量）与 `0x000F`（TIM 脉冲捕获）都是 2026-10 与用户确认新增的命令；两条各自独立
> （xlsx 原表只有 6 条命令，没有测量命令）。

> **⚠ 修正记录（第 7 轮，用户确认）**：`0x0112` 最初被误读成 `0x0070` —— xlsx 该单元格存的是**数值 `112`**，
> 我按十六进制理解成了 `0x70`。正确值是 **`0x0112`**，与测径治具的 PROGRAM 命令码一致。
> 其余命令在 xlsx 里是共享字符串（`"0A"`/`"0B"`/`"0C"`/`"0D"`）或数值 `9`（= `0x09`），不存在同类歧义。

### 2.3 通用状态码

| 码 | 名称 | 码 | 名称 |
|---|---|---|---|
| `0x00` | OK | `0x07` | ERR_INCOMPLETE 固件不完整（完整标志缺失） |
| `0x01` | BUSY 系统忙（非 IDLE 收到命令） | `0x08` | ERR_CRC（仅诊断，不回 ACK） |
| `0x02` | ERR_SIZE 文件大小异常 | `0x09` | ERR_SEQ（仅警告，不拒绝） |
| `0x03` | ERR_FLASH SPI Flash 读写失败 | `0x0A` | ERR_COUNT 上传字节数与声明不符 |
| `0x04` | ERR_PROG ISP 烧录失败 | `0x0B` | ERR_PARAM 参数错误 |
| `0x05` | ERR_TEST 治具测试失败 | `0x0C` | ERR_TIMEOUT 上传超时（10s 无新数据） |
| `0x06` | ERR_NO_FW 固件不存在 | `0x0D` | ERR_OVERFLOW 上传溢出 |
| `0xFF` | NIY 命令未实现 | | |

## 3. 架构

```
PC ──USB CDC──▶ 治具 U1 ──SPI2(PB12 CS)──▶ GD25Q128(16MB) 存被烧固件
                    │                        Slot0=Bootloader @0x00000
                    │                        Slot1=App        @0x10000
                    └──0x0112──▶ UART ISP (AN3155) ──▶ 外接被烧板 MCU
```

- 原理图这块板 = **治具**（U1 主控 + U2 副控）；**被烧 MCU 是外接的另一块板**（用户第 8 轮确认）。
- 与测径治具同构：外部 SPI Flash 存固件 + U1 做 ISP 烧录。
- 被烧板目标地址：Bootloader `0x08000000`(0x5000) + App `0x08005000`(0xA000)。

## 5. 与协议 xlsx 的逐条对照

| 命令 | xlsx 要求 | 实现 |
|---|---|---|
| `0x0009` | LEN=9：总帧数 u16 + 文件大小 u32 + 版本 3B | ✅ 大端解析；`len<9 / size=0 / size>限 / 帧数=0` → `02 ERR_SIZE`；擦除/写头失败 → `03 ERR_FLASH`；非 IDLE → `01 BUSY`；**另加 SPI Flash ID 自检**（见 §7.6） |
| `0x000A` | LEN=L：OTA 数据 | ✅ 攒 256B 页编程；溢出 `0D`；写失败 `03`；**错误锁存**（后续 DATA 帧只回原错误码、不写 Flash） |
| `0x000B` | LEN=0 | ✅ 刷残页 → 比对字节数（不符 → `0A`，**不写完整标志**）→ 写 `0xA5` → 回读校验 → 切槽 |
| `0x0112` | LEN=0；**烧录完成后才回 ACK** | ✅ 前置检查两槽（缺固件 `06` / 不完整 `07`）→ 启动**非阻塞 SWD 烧录状态机**（`swd_programmer.c`）；终态由主循环回**一次** ACK（SEQ 锁存为受理时的序号）；成功后紧跟一帧 `0x0024` 板子 SN（§7.35） |
| `0x000C` | LEN=4：状态码+3B 版本 | ✅ 优先级 App 槽 → Bootloader 槽 |
| `0x000D` | LEN=4：失败时 `00 FF FF` | ✅ `SWDP_QueryTargetVersion()`：**通过 SWD 直接读目标 App 分区**（`DUT_APP_ADDR + DUT_VER_OFFSET`）；读不到/全 `FF` → `06`，连不上目标 → `0C`。偏移 `DUT_VER_OFFSET = 0x20` **仍是占位**（等 FOC 工程给真值） |
| `0x000E` | LEN=1(mode)；mode=1 时**测试跑完才回 ACK** | ✅ 见 docs/07 §3-§4：非阻塞测试状态机（等稳定→与 U2 交换快照→比对→判定→回 77B）；mode=0 立即回最近一批，不触发测试 |
| 其它命令 | 状态码表定义了 `NIY(0xFF)` | ✅ 统一回 NIY |
| CRC 错误 | "仅诊断, 不回 ACK" | ✅ 直接丢弃，不回 ACK |
| 上传超时 | 10s 无新数据 | ✅ 自己发一帧 `0x000A`（`+0C`，**沿用最后一帧的序号**，见 `fw_upload.c` 的 `FwUpload_TimeoutCheck`），回 IDLE；不覆盖已锁存的错误码 |
| 非 IDLE 收命令 | "系统忙" | ✅ `UPLOADING`/`PROGRAMMING` 期间一律回 `01 BUSY` |

### 7.35 SWD 引脚落地 + DUT 分区改定 + SN 上报 + 文档全库对齐（第 31 轮）

**这一轮不是加功能，是把"图纸终于给了答案"的两件事落进代码和文档，并新增一条主动帧。**

**(1) SWD 两个脚落地（`docs/09` §2）**

2026-10-27 新版治具原理图把 **U1 自己的 SWD 口独立引出去烧 DUT**，于是原来占位的两脚有了真值：

| 项 | 现在 |
|---|---|
| `swd_config.h` | `SWD_CLK = GPIOA/GPIO_PIN_14/14u`（网络 `U1-SCLK`）、`SWD_DIO = GPIOA/GPIO_PIN_13/13u`（网络 `U1-SWD`）、`SWD_PINS_CONFIRMED = 1`、`SWD_USE_NRST = 0` |
| 旧的占位值 | PB10/PB11 → PB1/PB3（**只作历史留档，别再当现状**） |

**取舍（写清楚，免得以后当成 bug）**：PA13/PA14 在 F103 上就是 U1 自己的 SW-DP，
要拿它们当普通 IO 去"打"DUT，就必须把 U1 的调试口关掉。`stm32f1xx_hal_msp.c` 按 `SWD_FREE_DEBUG_PINS` 二选一：

| `SWD_FREE_DEBUG_PINS` | 执行 | `SWJ_CFG` | 能烧 DUT | 能调试/下载 U1 |
|---|---|---|---|---|
| **1（默认，生产）** | `__HAL_AFIO_REMAP_SWJ_DISABLE()` | `100` | ✅ | ❌ |
| 0（开发期临时） | `__HAL_AFIO_REMAP_SWJ_NOJTAG()` | `010` | ❌ | ✅ |

附带：`SWJ_CFG=100` 同时把 **PA15/PB3/PB4 一并释放成普通 IO**，其中 **PB4 = TIM3_CH1（B 相捕获）**，
所以生产配置下 ③ 的捕获不再依赖"单独关 NJTRST"。

**救砖 / 升级 4 条路（推荐序，`docs/09` §2.1.1）**：
① 短接 **H1（BOOT0↔3.3V）→ 复位 → 系统 bootloader → USART3 两针烧**（首选，且与 `SWJ_CFG` 无关）；
② Connect-under-Reset（NRST 未引出，要手扶复位）；③ `SWD_FREE_DEBUG_PINS=0` 重编一版；
④ 全擦后 `SWJ_CFG` 复位 `000`。

> ⚠ **真板烧录尚未实测**：上述结论来自电脑上的**模拟目标 + 编译证据**，一次真板都没跑过。

**(2) DUT（FOC 板）分区改定（`docs/09` §7 第 6 条）**

| 分区 | 旧占位值（作废） | 现在（按 FOC 工程确认） |
|---|---|---|
| Boot | `0x08000000` + `0x8000` | **`0x08000000` + `0x10000`（64 KB，扇区 0..3）** |
| App | `0x08008000` + `0xF8000`（992 KB） | **`0x08010000` + `0x80000`（512 KB，到 `0x08090000`，扇区 4 起）** |

`DUT_GO_ADDR = 0x08000000`（复位先跑 Bootloader）；`DUT_VER_OFFSET = 0x20` **仍是占位**（等 FOC 工程给真值）。
`flash_map.h` 里有一组编译期断言钉住"Boot 必须等于扇区 0..3、App 必须从 0x08010000 起、两段必须首尾相接"。

**(3) 新增主动帧 `0x0024` 板子 SN 上报（`sn_report.c/h` + `APP_SnReport()`）**

烧录成功后读被测板的 **96-bit UID**（`@0x1FFF7A10`，RM0090 Unique device ID）组 16B 主动推给 PC：

`[0]=算法版本 0x01`、`[1..12]=12B UID（大端）`、`[13]=12B UID 逐字节 XOR（不含版本号）`、`[14..15]=预留`

三条行为约定：**触发点是 `0x0112` 烧录成功后（在 ACK 之后发）**、**同板不重复上报**、**读 UID 失败静默跳过**。
模块只做纯逻辑（组帧/XOR/去重），不碰 SWD 和引脚，所以能宿主穷举测试（`test/sn_report_test.c`，22 项）。

**(4) `app_test` 的擦扇区断言改成按几何推导**

原来是"数出来的常数"（擦几个扇区、写多少字、多少 SWD 事务都写死），分区一改就得跟着改数。
现在改成**按分区几何 + F4 扇区表推导**，断言的是"推导值 == 实测值"，所以分区再变也只需要改 `flash_map.h`。
本轮实测：**擦扇区 = 5 / 编程字 = 102 / SWD 事务 = 764**（旧分区下的常数全作废）。

**(5) 文档全库对齐（本轮只动 `.md` / `.txt`，没碰任何代码）**

按"代码是唯一事实"把散在各文档里的**现状描述**统一到上面几条：
SWD 引脚占位 → 已确认、旧分区值 → 新分区值、命令条数口径（**20 条请求/应答 + `0x0024` 主动帧**）、
`LINK_CODE_VER` 0x0103 → **0x0104**、断言合计 **2436**、Keil 两片 **0/0**、**17 对副本**逐字节一致。
§7 里各轮的历史记录**保持原样**（那是对的），只在必要处补"已于 2026-10-27 确认/更正"。

**验证数字**：宿主 **2436 条断言 ALL PASS**（含 `sn_report` 22 项）；

### 7.1 帧接收缓冲区越界（第 1 轮，单测暴露）

原实现把帧解析直接放在中断里跑，一帧收完（`frame_ready=1`）后若上层还没取走，
后续字节会继续写 `frame_buf` 并把 `frame_pos` 一直加下去 → **缓冲区越界写**（内存踩踏）。
PC 把两帧粘连发出即可触发。

**修复**：改为「ISR 只压 512B 环形缓冲 + 主循环解析」，攒满一帧即停止出队。
> 同一套写法在参考项目 `diameter_JIG` 里也存在。

### 7.2 伪帧头导致长时间失步（第 1 轮）

头部只认 `A5 5B` 就无条件吃满 8 字节，遇到数据里出现的伪帧头会吞掉后续合法帧。

**修复**：`frame_resync()` —— LEN 非法时在已缓存字节里寻找下一个 `A5 5B` 重新对齐；伪帧头最终由 CRC 兜底。

### 7.3 ISP 擦除命令用错（第 2 轮，致命）

原实现照搬 G0 参考工程，只发 `0x44 Extended Erase`。
但 **`0x44` 是 bootloader v3.0+ 才有的命令；STM32F103 的 bootloader 是 v2.2，只认 `0x43`**。
若被烧板是 F103，**必然烧不进去**。

**修复**：握手后先读目标 bootloader 版本（AN3155 `0x01`），按版本决定先发 `0x43` 还是 `0x44`，另一个作兜底。
两条命令的全片擦除载荷都是 `FF FF 00`。

### 7.4 被烧板分区无边界校验（第 2 轮）

原来只校验 `size>0 且 ≤64KB-8`，未按槽位限制。若 Bootloader 镜像超过 `0x5000`，**会越界写坏 App 区**。

**修复**：`APP_ProgramPreCheck` 在**擦除之前**按槽位上限拒绝；`ISP_LoadImageHead` 再兜一层。

### 7.5 `ISP_WriteChunk` 的未使用形参（第 2 轮）

带一个 `data` 形参却从不使用（实际一直发模块内的 `s_buf`），是误用陷阱。已删掉形参并注明调用约束。

### 7.6 先擦除、后校验镜像头（第 3 轮，致命）

`ISP_ST_CONNECT` 原顺序是「握手 → 读版本 → **全片擦除** → 读头部校验 → 写」。
若镜像不合格（大小超分区 / 完整标志缺失 / 槽为空），**被烧板已经被擦掉却什么都没写进去 —— 板子报废**。
App 层的前置检查虽然挡得住，但 ISP 模块自身不该依赖调用方守规矩。

**修复**：改成**先把两段镜像头都校验通过（含分区上限），再擦除**；两段长度提前存进
`s_img_len_boot` / `s_img_len_app`。用例 T5/T9/T10 固化了这个顺序。

### 7.7 `GD25Q_ReadID` 比对常量错误（第 4 轮）

原实现（照搬参考工程）先发 3 个 dummy 再读 2 字节，并与 **`0xC817`** 比较。
查本地数据手册 `GD25Q128E Rev1.4`：JEDEC ID（RDID `0x9F`）= **`C8 40 18`**。
原实现读到的是 ID **之后**的字节，**在真实芯片上永远不可能相等** —— `GD25Q_Test()` 恒失败。

**修复**：正确返回 24 位 ID `0xC84018`，`GD25Q_Test()` 校验「制造商 `0xC8` + 容量 `0x18`」。

### 7.8 命令码读错（第 7 轮，用户指出）

见 §2.2 的修正记录：`0x0070` → **`0x0112`**。

### 7.9 PC 工具的两个可用性缺陷（第 8 轮）

1. 参数校验晚于开串口（`-p COM5 burn` 漏参数会先报串口错）→ 改为**先校验参数、再开串口**；
2. 端口打不开时抛裸 traceback → 改为友好提示 + 三条排查方向。

### 7.10 SPI Flash 提前自检（第 6 轮，新增能力）

`GD25Q_Test()` 此前无人调用、被链接器当死代码剔除。现接到 `0x0009` 的参数校验之后、擦除之前：
Flash 不在线 / 型号不对时，**第一条命令**就以 `03 ERR_FLASH` 暴露，而不是"擦除静默失败"或"上传到一半才报错"。
用例 T13 固化（RDID 返回全 0 → `0x0009` 回 `03`，且零擦除零写入）。

### 7.11 ISP 失败后没有恢复现场（第 9 轮，两处）

`ISP_SetFail()` 原来只改状态码，**不恢复任何硬件状态**：

- **BOOT0 一直保持高电平** → 治具持续把被烧板的 BOOT0 拉高，被烧板停在 bootloader，
  相当于被外部一直驱动一个启动配置脚。
- **ISP 串口一直停在 8E1** → 之后任何走这个口的**运行态（8N1）**收发都会因校验位不匹配而失败。
  典型表现：**第一次烧录失败之后，后面怎么都不对**。

**修复**：`ISP_SetFail()` 里把 BOOT0 拉回低电平、串口切回 8N1。
刻意**不**额外复位被烧板 —— 让它在 bootloader 里等下一次 `0x0112`，重试更直接。
（测径治具的 `ISP_Connect()` 失败时不做恢复，这里是刻意改进。）

另修一处：`BSP_ISP_UART_Init()` 原来把串口**上电就配成 8E1**，而那时还没有任何 ISP 会话；
改为上电默认 **8N1（运行态）**，由 `ISP_Start()` 在进入 bootloader 会话时才切 8E1。

### 7.12 补齐两块此前完全没有验证的契约（第 9 轮）

新增两个用例，把"我以为对"变成"已断言"：

| 用例 | 断言内容 | 编译配置 |
|---|---|---|
| **T14** | 进 ISP 切 8E1、**成功路径与失败路径退出时都必须回到 8N1** | 全部 3 种配置 |
| **T15** | BOOT0/RESET **波形**：先置空闲电平（BOOT0=0/RESET=1）→ BOOT0 拉高 → 紧接着 RESET 拉低 → 维持 ≥10ms → RESET 拉高；Go 之后与**失败之后**都必须把 BOOT0 放开 | `ISP_CTRL_PINS_CONFIRMED=1` |

> **T15 同时也第一次编译到了 `ISP_GpioInit()` 的函数体** —— 默认配置下那段被 `#if` 编译掉，
> 主机上从未构建过。新配置一上去就暴露了宿主 HAL 替身里缺 `GPIO_SPEED_FREQ_LOW` 宏的问题。

> **T15 第一版是我的测试写错了**：我假设"第 1 次 GPIO 写就是 BOOT0 拉高"，
> 但 `ISP_GpioInit()` 会**先**写空闲电平，所以真正的第 1、2 次写是 `BOOT0=0 / RESET=1`。
> 固件是对的，改成"定位 BOOT0 第一次拉高那一步再往后查"后通过。

### 7.13 控制脚 GPIO 端口时钟没开（第 10 轮，**只在打开 `ISP_CTRL_PINS_CONFIRMED` 后才暴露**）

`ISP_GpioInit()` 会把 **PC13（GPIOC）** 配成 RESET 输出，但
CubeMX 生成的 `MX_GPIO_Init()` 只使能了 **GPIOD / GPIOA / GPIOB**（板上实际用到 A/B），
**没有使能 GPIOC**。

STM32F1 上对"时钟未使能"的 GPIO 端口写 BSRR/BRR 是**静默无效**的。后果：
**RESET 永远不翻转 → 被烧板永远进不了 bootloader → 烧录必定失败**，而且没有任何报错线索。

**修复**：`ISP_GpioInit()` 里显式打开 GPIOA/GPIOB/GPIOC 三个端口时钟
（已使能的重复使能无害），这样以后把 BOOT0/RESET 改到任意 A/B/C 引脚都不会再踩这个坑。

> 这个 bug 从第 1 轮就在，但一直**不可见**：`ISP_GpioInit()` 的函数体整体被
> `#if (ISP_CTRL_PINS_CONFIRMED)` 包着，默认配置下根本不编译。
> 上一轮为了验证引脚波形加了 `pins` 编译配置，它才第一次被编译到 —— 一编译就暴露了。

**验证（T16，并证明测试有牙）**：宿主侧给 `RCC` 做了替身，测试直接断言 `APB2ENR` 的
IOPAEN/IOPBEN/IOPCEN 位。临时把三行时钟使能删掉重编：

```
[T16] 控制脚所用 GPIO 端口的时钟必须被使能
  FAIL: GPIOB 时钟已使能 (BOOT0)
  FAIL: GPIOC 时钟已使能 (RESET)
  FAIL: GPIOA 时钟已使能
    APB2ENR = 0x00000000        ← 修复前
```
恢复后 `APB2ENR = 0x0000001C`，全部通过。

### 7.14 PC 工具：`0x0009` 的 ACK 超时设置得太短（第 11 轮）

`foc_jig_tool.py` 的 `do_upload()` 用**默认 3 秒**等 `0x0009`（起始帧）的 ACK。

但 `0x0009` 在固件里会**触发扇区擦除**：按声明大小擦掉覆盖的 4KB 扇区，最大镜像 65528B → 最多 **16 个扇区**，
GD25Q128 单扇区擦除最长 **400ms** → 最坏约 **6.4 秒**。

> **后果**：真实硬件上会偶发"起始帧超时" —— 治具其实正在正常擦除，PC 却已经放弃了。
> 固件侧没有问题（擦除期间 `app_state` 还是 IDLE，不会误触发 10s 上传超时），纯粹是 PC 侧超时值不对。

**修复**：新增 `ERASE_TIMEOUT = 30.0`，`0x0009` 用它；超时提示里写明"该帧会触发扇区擦除"。

### 7.15 新增：一键烧录的镜像本地预检（第 11 轮）

`burn` 现在**在开串口之前**先把两个固件文件检查一遍（`preflight_burn()`）：

| 检查 | 硬错误? |
|---|---|
| 文件存在 / 可读 / 非空 | ✅ 是 |
| 不超过被烧板对应分区上限（Bootloader `0x5000` / App `0xA000`） | ✅ 是 |
| 向量表看起来像 Cortex-M 镜像（SP ∈ `0x2000xxxx`、复位向量为奇数 Thumb） | ❌ 仅提示不拦 |

两条设计考虑：
1. **放在开串口之前** —— 文件搞错不该先被"端口打不开"挡住；
2. **分区上限与固件 `flash_map.h` 的 `DUT_BOOT_SIZE`/`DUT_APP_SIZE` 对齐** ——
   提前拦下比"上传 40KB 后再被 0x0112 拒绝"省事，也避免操作员把 Boot 和 App 传反。

已用三个构造文件无硬件验证：正常文件→预检通过（随后才报端口打不开）；Bootloader 超限→**开串口前**被拒；
空文件→**开串口前**被拒。`selftest` 也加了 6 条纯函数用例（空/超限/正常/SP 异常/复位向量异常/Boot 超限）。

### 7.16 测量功能：整数 EMA 的滤波死区（第 13 轮，单测暴露）

**现象**：阈值阶跃测试里，V5 通道（α=1/64）从 5.000 V 阶跃到 4.000 V，
跑 600 次轮询后停在 **4.061 V** 不再收敛。

**根因**：指数滑动平均写成 `avg += (x - avg) >> shift`，当 `|x-avg| < 2^shift`
时增量被截断成 0。以毫伏为单位时 shift=6 的死区是 **±63 mV**
（3.3V 通道上相当于 1.9% 误差），相电压通道 shift=8 更是 **±255 mV**。

**修复**：内部换算与滤波一律改用**微伏**，死区降到 64 µV / 256 µV，
折算到输入侧 < 2 mV（可忽略）；同时把 `uV→mV` 的显示改成四舍五入。

**顺带修掉的同类问题**：滤波更新频率原本跟着主循环走（远高于 25 kHz 的 ADC 扫描率），
等效平均样本数会大幅减少、窗口时间常数也随环路频率漂移 →
改用 `DMA1_Channel1->CNDTR` 回卷判定"完成一轮扫描"，**一轮只更新一次**。

> 累计：**20 项缺陷**（含 **4 项致命**）。其中 13 项由测试/仿真发现、3 项由代码复查发现、
> 1 项用户指出、1 项 PC 工具时序、1 项工具链（7.17）、1 项自动化测试假通过（同 7.17）。

### 7.19 对着 ADIv5 规范核对，抓出 SWD 引擎两个致命错误（第 15 轮）

用户提供了 ADIv5 规范（IHI0031H）、F4 参考手册（rm0090）、Cortex-M4 编程手册（PM0214）
和 Arm 的 DAPLink 源码，于是把 SWD 引擎里**每一个常量**都对着资料核了一遍，抓到：

**① `FLASH_CR.STRT` 位号写错（致命）**：我写成 bit15，**RM0090 §3.9.7 明确是 bit16**。
后果：擦除命令根本不会启动，而 `BSY` 一直是 0 → 固件会"以为擦好了"继续编程，
直到撞上 PGAERR 才报错。**上板后永远烧不进去**，且现象会指向错误的方向。

**② `CSW.AddrInc` 语义记反（致命，影响回读校验）**：我按"0b00=自增 / 0b01=不自增"实现，
而 **ADIv5 表 C2-1 是反的**：`0b00 = Auto-increment off`（TAR 不变）、
`0b01 = Increment single`（每次 DRW 访问后自增）。
后果：`SWD_MemReadBlock()`（回读校验用它）会**反复读同一个地址**，
校验必然失败；DAPLink 的 `CSW_VALUE` 也正是 0x23000052（含 `CSW_SADDRINC`），佐证了正确取值。

**为什么测试全绿却没发现**：仿真模型是我自己写的 `sim_ap_inc()`/`T_CR_STRT` 也写了同一套错值——
**模型与固件共享同一个错误概念，自证式仿真抓不出来**。这是本次最大的教训。

顺带修掉两处（非致命）：
**③ 清 sticky 用写 CTRL/STAT**：SW-DP 上该位是 RO/WI 清不掉，而且会把 `CDBGPWRUPREQ`
一起清成 0（等于撤掉调试电源请求）→ 改成规范的 `ABORT = 0x1E`。
**④ 写事务尾部多打一个 turnaround**：ADIv5 §B4.1.1 明确 WDATA 之后"没有额外 turnaround"→ 去掉，
每个写事务省 1 拍（实测 87855 → 86647 周期/KB）。

**防回归**：新增 27 项"规范自检"（常量按手册字面值钉死 + 两条 CSW 语义用例）。
实测（当轮数据，见附录 B）：spike 86 项、宿主回归 1209 项全过，Keil U1/U2 均 0 Error / 0 Warning。

### 7.20 四路串口 + U1↔U2 链路：4 个坑（第 16 轮）

**① `Link_RequestPoll` 的 `*outlen` 一身二职 → 静默拷 0 字节**（宿主单测暴露，API 设计错误）。
原来把 `*outlen` 同时当"入参=缓冲容量"和"出参=应答长度"。调用方按习惯传了 `0`，
于是 `memcpy` 长度被截成 0：**函数返回成功、长度也对，数据却一个字节没拷**，
测试里看到的是栈上的旧数据（一眼看去像"内容错位"，很容易误判成收发丢字节）。
→ 改成固定容量契约：`out` 必须 ≥ `LINK_MAX_PAYLOAD`，函数恒拷 `resp_len` 字节。
教训：**别让一个参数既做输入又做输出**，尤其别把"容量"藏在输出参数里。

**② HAL 的 ORE（溢出）分支会悄悄关掉接收**（设计阶段按 HAL 源码抓出，未上板）。
`stm32f1xx_hal_uart.c` 的 ORE 路径是"先 `UART_EndRxTransfer()` 关 RXNEIE/PEIE/EIE 并把
`RxState` 置 READY，**再**回调 `HAL_UART_ErrorCallback()`"。
若错误回调里不重新 `HAL_UART_Receive_IT()`，这一路从此**永远收不到字节且不报任何错**。
→ `UartPort_OnError()` 里重挂接收（驱动不变量），`uart_cfg.c` 里先清 ORE 再分发；
宿主测试 §5 专门模拟"HAL 停了接收"并断言重挂成功。

**③ 假 HAL 的 TxCplt 重入让驱动"看起来在丢数据"**（测试自身的缺陷，值得记一笔）。
推线是嵌套的（发送完成回调里立刻发起下一段，又回到推线），
于是同一段数据被回调了两次 TxCplt → 驱动的 `tx_tail` 多推一格 → 后续内容整体错位。
真 HAL 每次 `HAL_UART_Transmit_IT` 只回调一次，**是仿真器写错了**。
→ `sim_tx_done()` 加幂等保护。教训：**仿真器与真实现的语义差，会伪装成被测代码的 bug**。

**④ UV4 在受限环境下"0 Error 却不产出 `.o/.axf/.map`"**（环境坑）。
Keil 的 UV4 以子进程方式跑 armcc/armlink；当构建环境限制子进程写文件时，
UV4 仍打印 `0 Error(s), 0 Warning(s)` 与 "linking..."/"FromELF..."，
但磁盘上只有 `.lnp/.sct/.dep` 和日志，没有任何产物——**"编译通过"是假的**；
更坑的是它会**先删掉旧产物**再链接，于是"失败的构建"还会顺手毁掉上一次的好产物。
→ 判断构建是否真的发生：看 `MDK-ARM/<target>/<name>.map` 时间戳是否刷新（本工程已用此判据复核）。

### 7.21 三个模块在两片各一份副本 → 加了"副本必须一致"的机械检查（第 16 轮收尾）

`uart_port` / `uart_link` / `protocol_frame` 在两片各自的工程目录里各有一份副本
（**不搞公共目录**：每个工程自包含）。代价是"改一边忘一边"，而后果是**静默的**：
字段布局变了而对面还是旧的 → STATUS 解出垃圾；帧格式变了 → 一直 CRC 错/超时。

加了两道机械保护：

1. **回归脚本第 7 阶段**用 `fc /b` 逐字节比对这 6 个文件对，不一致就 `[FAIL]` 并让回归退出码为 1。
   已反证：故意把 U2 的 `uart_port.c` 改一个字节 → 该阶段打印 `uart_port.c : DIFFERENT` +
   `[FAIL]`、回归退出码 1；还原后恢复 `[PASS]`。
2. **`LINK_CODE_VER`**（`uart_link.h`）：改变链路对外行为的改动 +1，
   从机在 STATUS 里回这个值，主机每 5 次保活探测（≈2.5 s）比对一次，
   `APP_U2VerOk()` 直接给出"两片是否同一版代码"。
   宿主测试新增 11 项断言覆盖"同版本通过 / 旧版本被检出 / 空指针安全"。

两片各自的编译产物、烧录判据与副本规则写在 `docs/10_UART四路驱动设计.md` §10。

### 7.22 ④ 脉冲捕获：三个真问题（第 17 轮）

**① 占空比被"多一个高电平段"带偏**（算法错误，单测抓出）。
一开始用"高电平总和 / 总时间"算占空比。但相邻边沿的区间数＝边沿数−1（奇数），
高、低两组的样本数会差 1 → 20kHz/50% 会算成 **34.7%**。
→ 改成**高、低各自取平均再合成**：`duty = avg_high / (avg_high + avg_low)`。
教训：**比值类统计必须先保证两边的样本数可比**。

**② 毛刺/丢沿会把平均值污染，但离群剔除不能"一刀切"**。
用中位数剔除异常区间是对的，但**必须按高、低两组各自取中位数**：占空比 10% 时高电平段
天生比低电平段短得多，用全体中位数当基准会把正常的高电平段全当异常丢掉（单测覆盖）。
现在的规则：偏离本组中位数 1/2~3/2 之外就丢，并置 `PULSE_F_DIRTY`。

**③ `mode=0` 只读应答被截断成 77 字节**（真 bug，全链路单测抓出）。
应答布局从 77B 扩到 167B 后，`APP_MeasCmd` 的只读分支仍然写死了旧长度
`APP_SendAck(cmd, s_meas_resp, MEAS_PACK_RESP_LEN)` → PC 会按 77B 解析、后面两段脉冲
读不到。→ 改成用打包函数的**实际返回长度**。
教训：**"别人返回的长度"永远不要用常量替代**，否则扩布局时一定漏一处。

另外顺手修掉一个**硬件隐患**：`tim.c` 原来把 TIM4（PB6/7/8）等配成 PWM 推挽输出，
会把同一根线上的信号压死、等于跟对侧对打。
→ 改成输入捕获 + 引脚输入（含下拉），再生成须知写在 `docs/05` §2.5。

> ⚠ **2026-10 更正**：上面括号里原写的是"经 3kΩ 会把被测板的三相输出节点拉低（连带相电压 ADC 读数偏低）"。
> 那句话基于一个错误接线前提 —— `PB6/7/8` 实际接的是**编码器座 CN2 的 A/B/Z**（3kΩ 是**上拉**到 3.3V），
> 不是电机输出端。隐患本身是真的（而且比原来写的更严重：**U1 和 U2 都挂在同一根线上**，
> 两片推挽输出 + 编码器 = 三个驱动源），但原因不同。详见 §7.22 与 `docs/00` §3.5。

### 7.17 烧录方案换成 SWD：三处踩点（第 14 轮）

1. **`test/run_all_tests.cmd` 被改成 LF 换行 → cmd.exe 解析错乱**（严重：**假通过**）。
   `edit` 工具写回文件时用了 LF，cmd.exe 对 LF-only 的 .cmd 会把命令切碎执行，
   结果是所有测试**都没跑**，却打印出 `===== host tests: ALL PASS =====`。
   → 修法：把 .cmd 文件强制转回 CRLF；并在文档里记下这条教训
   （**改完 .cmd 必须检查换行**，否则会得到"看起来全绿"的假结果）。
2. **分区大小算错**（`DUT_APP_SIZE` 写成 0x78000，正确是 `0x100000-0x8000 = 0xF8000`）。
   被 `flash_map.h` 新加的编译期断言 `dut_app_must_end_at_flash_end` 在**编译期**拦下
   ——这正是当初加那批静态断言的目的。
   > （已于 **2026-10-27** 按 FOC 工程更正：分区是 Boot `0x08000000`+`0x10000`、App `0x08010000`+`0x80000`，
   > 上面那句 `0xF8000` 是当时的占位值，现在只作历史；见 §7.35。）
3. **`0x000D` 的语义变化**：UART 时代读不到就回 `ERR_TIMEOUT`；
   SWD 能直接读到目标 Flash，于是"读得到但全 0xFF（App 区为空）"应回
   `ERR_NO_FW(0x06)` 而不是 `OK`＋`0xFF 0xFF 0xFF`。全链路测试相应更新。

### 7.18 SWD 引擎：模型与主机约定不一致导致的"假失败"（第 13 轮 spike）

spike 第一次跑起来时**第二批事务全部 NO_ACK**、总线冲突 118 次。
根因不是协议写错，而是**包同步规则不严谨**：模型早期用"8 位滑动窗口匹配请求头"，
窗口里残留着**上一个包头**的比特，导致在真包头之前 5 位就误判成包头。
→ 改成按 ADIv5 的做法：**空闲电平为低、Start 位(1) 的上升沿标记包头**
（并在主机侧补一个 spec 允许的空闲周期，让上升沿一定出现）。
修好后 59 项断言全过、冲突与奇偶错都为 0。

### 7.34 给上位机补三条命令 + 命令大全整理（第 30 轮）

**起因**：上位机工程师要开工，问"这几个核心功能有 PC→治具的命令路径吗"。
答案是"有，但 ⑤ 要 PC 串 5 条还要自己比三个数、没有设备自检、每块板要发 8~12 条"，
于是补了三条（用户批准："开工，顺便命令样式整理成 INFO/命令大全.txt 这样"）：

| 命令 | 作用 | 关键设计 |
|---|---|---|
| **`0x0017` GET_JIG_STATUS** | 设备自检/在线状态，32B | **只读、不改状态机 → 放在 BUSY 闸门之前**，任何状态都能问（上位机最需要它的时刻恰恰是治具忙的时候）。回：状态机、U2 是否在线/版本是否一致、链路与串口错误计数 |
| **`0x0018` ENC_JUDGE** | ⑤ 的三方对齐判定，29B | 判据抽成纯函数 `enc_chk.c`（**58 条宿主断言**）；三个数由 PC 喂进来，治具**不缓存任何状态** |
| **`0x0010` RUN_ALL** | 一键跑完 ②③④⑤⑥，29B | **不重写子流程**：直接复用 0x0015/0x000F/0x0016/0x0012/0x0013/0x0014 和 DUT 透传，只负责"按顺序点火 + 采每步结果 + 汇总"。12 步、每步独立超时、失败不中断 |

**⑤ 的判定层补上了**：之前 ②④⑥ 都有判据层（vol_chk/phase_chk/cur_chk）而 ⑤ 没有，

1. **子命令的应答照常发给 PC**（同 SEQ），最后再回 0x0010 的汇总 —— 这样"单独调"和"一键跑"是**同一套实现，

2. **烧录不在里面**：0x0112 要几十秒，塞进去会让超时和失败恢复复杂化。推荐"先烧录成功，再一键测试"。

### 7.33 并发缺陷 D4/D5/D6 收尾（第 29 轮）

**这一轮不是加功能，是把 `docs/03` §4 里挂了三轮的三个并发缺陷清掉**
（用户批准的是"修复并发缺陷 D4/D5/D6"）。三处都在"ISR ↔ 主循环"上，
其中 **D6 和 D5 是可触发的**，D4 更像"靠语句顺序侥幸躲过"（下面分开说）。

**D6（`uart_port.c` 发送段长倒推）—— 危害最大的一条**

老代码在发送完成中断里用"**当前** `tx_head − tx_tail`"倒推这一段的长度。
可是主循环在发送期间还能继续往环里塞字节（115200 下 87 µs/字节，一帧要几百 µs），
`head` 早就往前走了 → 倒推出来的长度比实际发的长 → `tx_tail` **跳过还没发出去的字节**
→ 对端收到半截帧/CRC 错，而本地计数器（`tx_drop`）一点异常都没有 —— **静默丢字节**。

修法两步：
1. 新增 `tx_len`：`uart_tx_kick()` 把"这一段交给 HAL 的长度"存下来，
   `UartPort_OnTxComplete()` **按 `tx_len` 推进 tail**，不再读 `tx_head`。
   于是不变式变成：`tx_busy≠0 ⟺ tx_len≠0 ⟺ HAL 手里正有一段在发`。
2. `kick` 的「判断 + 置位 + 调 HAL + 失败回退」整体放进 `__disable_irq()` 临界区，
   而且是**先进临界区再判断**（先判断再关中断是不够的：两步之间完成中断可以插进来，
   把 busy 清 0 并由它自己 kick 一段出去，随后我们这次 HAL 调用就撞 HAL_BUSY，
   回退又把 `busy/tx_len` 清掉 → 与中断手里那一段彻底错位）。
   失败回退另外把 `tx_len` 也清 0，并新增 `uart_stats_t.tx_err` 计数 —— 这种路径
   正常应恒为 0，非 0 就说明驱动/外设状态不同步，别再靠"静默卡死"。

**D5（`pulse_cap.c` 的边沿环复位）—— 可触发，U2 是高发侧**

`PULSE_Start()` 连着写 `total / count / head` 三个字段，中途被捕获中断插进来就不成对。
**触发路径是真实的**：`u2_app.c:202` 收到 U1 的 ARM 时直接 `PULSE_CfgStart(win)`，
而 U2 的滚动窗口（每 200 ms 一次）随时可能正在跑。

**D4（`pulse_cfg.c` 的溢出计数清零）—— 老实说：老代码下不可复现**

"关 DIER 挡不住已排队的 NVIC 请求"这个**机制**是真的，但我把老代码逐句排过一遍：
`SR = 0`（清 UIF）在 `s_ovf3 = 0` **之前**，而"计数器刚被 `CNT=0` 复位后又要溢出"
需要 0.91 ms，所以排队的那一发进来时读到的 `SR` 里已经没有 UIF → 不会多自增。
也就是说**老代码是靠一个偶然的语句顺序躲过去的**。本轮把它改成显式保证，不再靠运气。

**修法（D4+D5 一处临界区一起解决）**：`PULSE_CfgStart()` 的顺序固定为
`__disable_irq()` → 关 NVIC 三个向量 → **清三个 pending** → 清 `CNT/SR/计数/极性`
→ `PULSE_Start()` 清边沿环 → 重新使能 NVIC → 开 DIER → `__enable_irq()`。
**清 pending 必须在动状态之前**（SR 里残留的标志会在重开 NVIC 的瞬间又置起一次 pending），
整段约几十个周期（<2 µs），不会把 115200 的收字节挡丢。
另外在 `pulse_cap.h` 写明：`PULSE_Start()` 只能在"捕获中断已关 + pending 已清"的临界区里调，
固件里**唯一**的调用者是 `PULSE_CfgStart()`。

**验证（这一轮的重点是把"没有验证过的东西"补上）**

`pulse_cfg.c` 是 ISR 层唯一碰寄存器的模块，而它**此前没有被任何宿主测试编译过**
（`app_test.c` 里是把 `PULSE_CfgStart` 整个换成替身函数）—— 所以开窗临界区从没被验证。
本轮新增：

### 7.32 任务 ④ 接上出口：`0x0016` 三相输出判据（第 28 轮）

**这一轮补的是一个"死代码"空白**：上一轮做完 `phase_chk`（62 项宿主单测）之后，
**没有任何人调用它** —— 也就是说 ④ 的判据层写完了、测过了，但**从外部用不到**，
链接器会把它整段丢掉（U1 的 Program Size 当时一动不动，就是证据）。

**修法**：加 PC 命令 `0x0016 MGR_CMD_PHASE_JUDGE`，它**没有状态机** ——
就是把"上一个测量快照（相电压 + 母线）"和"上一个捕获窗口的脉冲结果（占空比）"
喂给 `phase_chk` 判一遍，立刻回 **34B 报告**。

**为什么不做成"一条命令跑完采集+判定"**：采集那一段（ARM 两端同窗 + 200ms 窗口 + XCHK）
已经由 `0x000F mode=1` 做好了，再养一套编排状态机是重复。
所以 ④ 的用法是 **PC 按顺序发三条**：

```
① 0x0011 透传 DUT_PWM          → 让被测板输出已知 PWM（被测板固件实现）
② 0x000F mode=1                → 开窗采集（含 ARM 两端同窗）
③ 0x0016 mode=1 duty=<占空比>  → 判定（本命令）
```

请求 7B = `mode(1) + duty_a/b/c(各 2B, ‰)`；`duty = 0xFFFF` 表示该相高阻（不判）。
应答 34B = `状态(1)+汇总(2)+相数(1)` + 每相 10B（`flags + expect_mv + err_mv + tol_mv + duty_pm`）。

**T22 走通了整条数据通路（不是只验结构）**：
用 `MEAS_TestInject` 灌入"母线 24000mV、三相各 12000mV"，
配上 T15 那套假波形给出的 500‰ 占空比 → 期望值 500‰×24V = 12V = 实测值
→ **三相都判成 `OK`、命令状态 `OK`**。这三条断言（期望值 12000mV、三相 OK、状态 OK）
一起证明了：注入 → EMA 收敛 → 快照 → `phase_chk` → 报告 整条链路是通的。

**一个被"量化"绊了一下的断言**：我一开始把容差钉死成 1200mV，结果失败——
母线读数被整数 EMA 量化到 23999 而不是 24000，`tol = (23999/100)*5 = 1195`。
改成范围断言（1195~1200）并在注释里写明原因。**这不是 bug，是量化**——
但它提醒了一件事：**凡是经过 EMA/定点的量，断言要留量化余量**。

**验证**：宿主回归 **2200 项 ALL PASS**（app_test 311→337、DUT 模式 341→367）；
两片 Keil **0 Error / 0 Warning**；U1 ROM **+740 B**（`phase_chk` 真的进编译了）；17 对副本一致。

### 7.31 任务 ②：电压检测判据落地（第 27 轮）

**先说清 ② 到底缺什么**（免得重复造轮子）：
9 路模拟量的**采集、换算、门限判定、U1↔U2 交叉校验**早在 `0x000E` 里就有了（`docs/07`）。

**三个设计要点**

1. **`adc_mask` 由 DUT 自己声明**（INFO 里的能力位图）。**没声明的通道直接算"不判"**，

### 7.29 任务 ⑥（上半）：相电流判据层（第 25 轮）

**任务 ⑥ 要回答的问题**：被测板的电流采样链路（采样电阻 → 放大器 → ADC → 固件换算）对不对？
做法：**让被测板真的通一个电流**（`DUT_CURRENT` 静态通流：上桥 A、下桥 B），
治具采一遍它送出来的电流检测信号，再问被测板"你自己采到多少"，两边一比。

**关键设计决定：比「通流前 / 通流中」的差值，而不是比绝对值。** 两个理由：

1. 治具和被测板是**两套 ADC + 两套参考电压**，绝对值天然有差；
2. 更要紧的是——**被测板的电流放大器拓扑我们还不知道**（`docs/15` 待确认项 D4）：
   它可能是**中点偏置**的（零电流输出 1.65V），也可能以 0V 为地（零电流输出 0V）。
   **比差值就把这两种拓扑统一了**：零电流的偏置被减掉，剩下的就是"电流引起的那个变化量"。

所以 ⑥ 的判据是三条：

| 判据 | 含义 | 判失败吗 |
|---|---|---|
| **通流检查** | 两边变化量都小到几乎没有 → 电流根本没流起来 | ✅ 真故障 |
| **一致性** | 两边变化量之差 ≤ 容差 → 它们测的是同一个电流、换算也对得上 | ✅ 真故障 |
| **数据可用性** | 任一侧数据不可用（快照无效 / 贴边 / DUT 没报） | ❌ **不判**（同 ②④ 的规矩） |

**一个容易写错的地方（有单测盯着）**：**只有一边动了**时不能算"没通上电流"，
要算"两边对不上"。比如治具看到 0mV 变化、DUT 报 350mV 变化 —— 那是**不一致**，
不是"没通流"。这两种旗标指向完全不同的排查方向（查负载/供电 vs 查采样链路）。

**新增**：`U1/Core/Inc/cur_chk.h` + `Src/cur_chk.c`（纯函数、只 U1 用、不做两片副本）
+ `test/cur_chk_test.c`（**43 项**）。容差 = `max(对侧变化量的 5%, 30mV)`。

**验证**：`test/cur_chk_test.c` **43 项全过**（含容差边界、负变化量、只动一边、
三种"不判"、从快照取通道的正确性）；两片 Keil **0 Error / 0 Warning**；回归 **ALL PASS**。

**⑥ 还差**：把流程串起来的编排（读基线 → 通流 → 等 → 再读 → 判定 → 出报告），
以及 DUT 按 `docs/15` §7.7（`DUT_CURRENT`）/§7.8（`DUT_GET_ADC`）实现。

### 7.28 任务 ⑤（下半）：U2 回环采集 + 内部链路 ENC_XCHK（第 24 轮）

**目标**：U1 发出去的那串脉冲，**真的到线上了吗**？让 U2 数一遍。
这是三方对比（治具意图 = U2 实测 = DUT 上报）里的**第二环**。

**关键设计决定：编码器采集不走 `pulse_cap`，用独立计数器**

`pulse_cap.c` 是**单例**，而 U2 的滚动窗口一直在采 MA_IN 组（③④ 要用）。
一开始想的办法是"给 pulse_cap 加个采集源切换"（还要改 ARM 的语义去通知 U2）。
后来发现更省事的路：**⑤ 只需要"数了多少个边沿"，不需要周期/占空比** →
给编码器线配一套**自己的计数器**（`U2/Core/{Inc,Src}/enc_cap.c`），
于是两组**可以同时采**，不用切换、不用动 ARM、也不用改 45B 布局。

| 新增/改动 | 说明 |
|---|---|
| `U2/Core/{Inc,Src}/enc_cap.{h,c}` | TIM4 输入捕获（PB8/PB7/PB6 = A/B/Z），只数边沿；**一直使能、自由计数** |
| `LINK_CMD_ENC_XCHK 0x0109` | 请求 1B 动作（0 清零 / 1 读取），应答 15B = `status + A/B/Z(u32×3) + lost(u16)` |
| `Link_EncPackReq/UnpackReq/PackResp/UnpackResp` | 载荷编解码（放 `uart_link.{h,c}`，两片副本共用一份实现） |
| `LINK_CODE_VER 0x0103 → 0x0104`、`LINK_CAP_ENC_XCHK`(bit8)、`LINK_CAP_ALL` → `0x01FF` | 按规矩升版本号；能力位图加一位 |
| `MGR_CMD_ENC_PEER 0x0013` | PC 侧命令：把 `ENC_XCHK` 透传到 U2 并回带结果 |
| `U2/Core/Src/tim.c` | `MX_TIM4_Init` 由 **PWM 输出**改**输入捕获**（U2 侧这三个脚必须是输入——U1 那边是输出） |

**⑤ 的治具侧闭环就两步**（都不依赖 DUT）：
```
0x0012  → U1 发脉冲（默认 A=1000@5kHz / B=2000@10kHz / Z=1）
0x0013 action=1 → 问 U2 数到几个 → 和"打算发多少"对表
```
（`0x0013 action=0` 用来在发之前清零。）

**单测抓出的两个真问题**

1. **`0x0013` 会在内部链路忙时直接回 BUSY。** 内部链路上随时可能有一发保活探测在飞，
   早先的写法是"发不出去就回 BUSY"—— 结果是**"PC 发命令的时机碰巧撞上保活探测就失败"**，
   这不是调用方的错。改成**先把请求挂起来**，由 `APP_EncPeerTask` 等链路空出来再发（有上限）。
2. **死锁：`APP_LinkTask()` 只在 `app_state == IDLE` 时推进。**
   我们一进入 `ENC_PEER`（非 IDLE），那一发**在飞的探测再也没人轮询**，
   它的 `waiting` 标志永远是 1 → `Link_RequestStart` 永远返回 0 → 命令永远等不到应答。
   现象是"命令看起来不工作"，其实只是链路被一发探测占住了。
   修法：进入命令时先用 `Link_RequestPoll(&link, 0, 0, 0)`（"只巡一遍"）
   把陈旧请求收尾 —— 这是 `timeout_ms = 0` 那个语义的正当用法。

**还踩到一个"是替身的问题、不是固件的问题"**：宿主的 `HAL_UART_Transmit_IT` 在
`g_u2_on == 0`（模拟"线没接"）时**故意不回调 TxCplt**，而驱动的 `tx_busy` 只能靠 TxCplt 清
→ 一旦在"对端不在"的状态下发过一次，那个端口就被**永久钉住**。
这是替身的局限（真 HAL 总会给回调或报错），但会让**后面**的用例莫名其妙全挂。
T19 明确要"线是通的"，所以开头先 `UartCfg_Init()` 拿一个干净起点，并把这个原因写在注释里
（免得下次有人以为是固件 bug）。

**顺手修掉的测试脆性**：`uart_test` 里 `caps` 那条断言**把 `0x00FF` 写死了**，
v1.4 加了 `ENC_XCHK` 之后误报一次。改成用 `LINK_CAP_ALL` 推导位置 + 另外显式钉住新值。

**验证**：宿主回归 **2014 项 ALL PASS**（uart_test 882→913，app_test 292→311）；
两片 Keil **0 Error / 0 Warning**；U2 ROM +508 B；U1 ROM 37720 B；17 对副本逐字节一致。

**⑤ 还差一条腿**：DUT 上报它自己数到的计数（`docs/15` §7.9 的 `DUT_GET_ENC`）——
那需要 FOC 固件团队按规格实现。

### 7.27 任务 ⑤（上半）：编码器脉冲发生（第 23 轮）

**目标**：U1 从 CN2 的 A/B/Z 发出**定量脉冲串**，让被测板去数。
三方对比（治具意图 = U2 实测 = DUT 上报）里的**第一环**。

**分两层，因为一层能测一层不能**：

| 文件 | 内容 | 能不能宿主测 |
|---|---|---|
| `enc_plan.{h,c}` | 参数校验、频率→PSC/CCR、时长估算 | ✅ 纯算术，**50 项** |
| `enc_gen.{h,c}` | TIM4 寄存器 + GPIO + 中断 | ❌ 板级，宿主机编译不了（同 `pulse_cfg.c`） |
| `test/app_test.c` T18 | 请求解析 / 参数校验 / 非阻塞状态机 / ACK 布局 | ✅ **23 项**（`enc_gen` 用替身） |

**为什么拆**：频率→CCR 这种换算是**最容易算错、又最难上板发现**的部分
（错了就是"数出来的个数不对"，可能查半天），必须能在宿主机上反复跑；而寄存器那层本来就没法测。

**技术选型：输出比较"翻转"模式（OCxM = 011），不是 PWM**
三路要发**不同的个数**，A/B 的**频率还可能不同**。
翻转模式下每路的翻转时刻由**自己的 CCR** 决定 → 三路各走各的频率、各自数自己的翻转次数、
到数了就单独停，互不干扰。（PWM 模式三路共用一个 ARR，只能同频。）

**一个必踩的坑**：**输出比较的 `CCxIF` 必须写 0 清**，
不像输入捕获那样"读 CCR 就自动清"。把 `pulse_cfg.c` 的写法直接搬过来
→ 中断反复进来、计数飞涨、发出去的脉冲数完全不对。代码里显式写了这一步并加了注释。

**安全设计**（这三根线 U2 也挂着，见 `docs/12` §2）：
- 空闲态 PB6/PB7/PB8 **一律输入**；只在发的时候切成 AF 推挽；
- 发完（或超时强停）**立刻收回输入态** —— 不收手就是"两片推挽输出 + 编码器抢一根线"；
- 超时兜底：`EncGen_Poll` 按 `EncPlan_DurationMs + 100ms` 强停并置 `EncGen_Aborted()`，
  上板看到这个位为 1 就要查（多半是引脚没配成 AF，或 CCxIF 没清干净）；
- 启动前 `NVIC_DisableIRQ + ClearPendingIRQ` 再复位计数（就是 `docs/03` §4 对 D4 的建议修法）。

**参数（用户给的，做成可传）**：A=1000 个 @5kHz、B=2000 个 @10kHz、Z=1 个。
**三路个数故意各不相同** → DUT 报回来就能唯一确定是哪一路接错/没接。

**新增 PC 命令 `0x0012`**：请求 12B（或 LEN=0 用默认），应答 9B =
`状态(1) + 完成掩码(1) + 超时位(1) + A/B/Z 实际翻转次数(2×3)`。
**带上实际翻转次数是关键**：上板时一眼就能看出"到底发出去没有"，
不用只靠示波器——这条命令让 ⑤ 的上板调试不需要 DUT、不需要编排。

**单测抓到一个设计问题**：一开始参数校验只写在 `enc_gen.c` 里，
命令层（`app.c`）直接就把请求丢给发生层。两个坏处：
① 违反"参数校验先于动作"的既有规矩；② 发生层是板级的，宿主机测不到，**错误路径等于没测**。
改成**命令层自己也校验一遍**（`EncPlan_Check`），发生层再校验一次（纵深防御）。
这个 bug 正是 T18 的"频率 50Hz → 0B"用例逼出来的。

**验证**：宿主回归 **1964 项 ALL PASS**（T18 让 app_test 从 269→292 / 278→301）；
两片 Keil **0 Error / 0 Warning**；U1 ROM +1788 B（`0x0012` 那条路真的接上了）；
U2 的 Program Size **一个字节没变**；17 对副本逐字节一致。

**还差**（下一轮）：U2 把 TIM4 配成输入捕获采这三根线（回环），
以及把"U2 实测 / DUT 上报"和"治具意图"对起来。

### 7.26 任务 ④：三相输出检测的判据层（第 22 轮）

**为什么走 ADC**：`MA0_OUT` 组在硬件上**只有 ADC 通路**（§7.23 查实），所以"捕获电机输出端的
周期/占空比"做不到。能做的是读**相电压平均值**。

**一条判据覆盖两种用法**（这是这一轮最省事的设计决定）：

```
期望相电压 = expect_permille(‰) × 母线电压 / 1000
判定       = |实测相电压 − 期望相电压| ≤ 容差
```

- **PWM 模式**：`expect_permille` = 命令给的占空比 → 判据变成 `V ≈ D × VBUS`；
- **静态电平模式**：`expect_permille` = 0 或 1000 → 就是"静态低/高"判据。

**不用写两套代码，静态电平只是 PWM 的两个端点。** 这条判据还比"两端周期一致"信息量更大：
它同时验证了**驱动级有没有正常工作**和**母线电压采样对不对**。

**新增**：`U1/Core/Inc/phase_chk.h` + `Src/phase_chk.c`（纯函数、只 U1 用、
**不做两片副本**——判定只在 U1 做，同 measure 的既有原则）+ `test/phase_chk_test.c`（**62 项**）。

**四种"不判"都必须不算失败**（这是判据层最容易写错的地方，专门测了）：

| 情况 | 为什么不能判 | 旗标 |
|---|---|---|
| 该相**高阻/关断** | 节点浮空，读什么都没意义 | `HIZ` |
| **母线太低**（< 5 V） | 期望值本身太小、噪声占主导 | `VBUS_LOW`+`NODATA` |
| 电压/母线**数据不可用**（快照无效、贴边、溢出） | 读数不可信 | `NODATA` |
| 该相本来就不该有输出（命令占空比 0）+ 捕获无信号 | 正常现象，不是故障 | 不置旗标 |

**一个真会被写错的地方**：静态电平测试里**没有 PWM 边沿**，如果无脑查"捕获到信号了吗"，
每个静态电平用例都会误报 `NOSIGNAL`。所以输入里有一个 `expect_pwm` 开关，
**只在 PWM 模式查脉冲**——这条有专门的单测盯着（"静态高电平 + 捕获无信号 → OK"）。

**顺手做的交叉核对**：PWM 模式下 if 捕获测到的占空比与命令不符（>5%）→ 置 `DUTY_DIFF`。
这本是 ③ 的活，但它和 ④ 用的是同一份数据，一起判不额外花钱。

**验证**：`test/phase_chk_test.c` **62 项全过**（含容差边界"正好等于容差算过、多 1 mV 算不过"）；
两片 Keil **0 Error / 0 Warning**；回归 **ALL PASS**。
U1 的 Program Size **一个字节没变**——`dut_proto.c` / `phase_chk.c` 虽然进了 Keil 工程，
但暂时没被调用，Keil 把未用段去掉了（等编排接上才会占空间）。

**教训**：判据层的测试，重点不是"算出对的数"，而是**"什么时候不该判"**。
这一轮 62 项里有 14 项专门测"不判"，正是它挡掉了"静态电平误报无信号"这个必然踩的坑。

### 7.25 任务 ③：把"哪片测哪组"改对（第 21 轮）

**问题**（§7.23 查出的）：U1 原来用 `TIM4 ← PB6/PB7/PB8` 采"电机输出端"，但那三个脚实际是
**编码器座 CN2** 的 A/B/Z；`MA0_OUT` 组在硬件上**只有 ADC 通路**。
于是 `0x000F` 拿"U1 的编码器线"和"U2 的驱动信号"互判"两端一致" —— **比的是两组毫不相干的信号**。

**改法**（算法层、45B 线格式、ARM 窗口**一行没动**）：

| 文件 | 改动 |
|---|---|
| `U1/Core/Src/pulse_cfg.c` + `.h` | 绑定改成 `TIM3_CH2(PB5)=A` / `TIM3_CH1(PB4)=B` / `TIM1_CH1(PA8)=C`，与 U2 一致；**两片做成逐字节副本** |
| `U1/Core/Src/tim.c` | `MX_TIM1_Init` 由 **OC 输出**改**输入捕获**；`MX_TIM3_Init` 由 **PWM 输出**改**输入捕获**；TIM4 引脚保持输入（留给 ⑤）；三处 MspPostInit 注释照实改 |
| `test/run_all_tests.cmd` | 副本比对清单 15 → **17** 对（`pulse_cfg.c` / `pulse_cfg.h` 进清单） |

**验证**

- 两片 Keil **0 Error / 0 Warning**；U1 ROM **36836 → 35676 B（−1160）**、RAM 12368 → 12376 B。
  ROM 变小是因为去掉了 OC/PWM 那条初始化路径（`HAL_TIM_Base_Init` + `HAL_TIM_ConfigClockSource` +
  `HAL_TIMEx_ConfigBreakDeadTime`）。**U2 的 Program Size 一个字节没变**，正好反证"两片副本确实一致"。
- 回归 **ALL PASS**，17 对 `fc /b` 逐字节一致。

**为什么没有牺牲 ADC**：`TIM3_CH1/CH2` 的默认复用脚是 `PA6/PA7`，那是 U1 的 A/B 相 ADC 脚；
但 `PB4/PB5` 是它的**部分重映射**脚，而 U2 本来就用 PB4/PB5 → U1 照抄 U2 的 `tim.c` 即可，**零代价**。

**教训**：`fc /b` 这种"机械一致性"检查，**加进清单才算数**。
`pulse_cfg.c` 之前不在清单里，所以 U1/U2 各写各的、谁是"对的那份"全靠人记 —— 这正是错绑定的温床。

### 7.24 任务 ①：DUT 通讯协议 + 治具侧链路（第 20 轮）

**做了什么**

1. **`docs/15_DUT通讯协议规格.md`** —— 给 FOC 固件团队的规格：9 条命令（`0x0200~0x0208`）、

**这一轮单测抓出的真 bug（都是"照着写完就算过"会漏掉的）**

| # | bug | 后果 |
|---|---|---|

### 7.23 原理图接线核对：一条错结论扩散了四份文档（第 19 轮）

**起因**：规划 ①~⑥ 测试任务时，需要确认"治具能不能往外发信号"，于是重查原理图。

**查出两件事：**

**(1) 追踪工具本身有 bug（已修）。** `tools/sch_trace.py` 判多边形闭合用 `d.strip().endswith('Z')`，
而 pdftocairo 把闭合矩形写成 `M x0 y0 L … L x0 y1 Z M x0 y0` ——
**闭合的 `Z` 后面还跟着一个只有 moveto 的空子路径**，字符串末尾是 `M x0 y0` 而不是 `Z`，
所以判定恒为 False，"剔除器件外框"整段代码**从未生效**（证据：修好前全图 `bodies` 剔除数 = 0，
而实际应剔除 61 个）。后果：一颗 48 脚 IC 的全部引脚会通过本体外框在几何上连通成一块 ——
`net U1-RX1` 能返回 178 段，把 `VBAT`/`VDD_3`/48 个脚号全拉进来。

**修法**（2026-10）：① 闭合改成**按几何判**（首尾同点，容差 0.3pt）；
② 按 `M` 拆子路径（顺带修掉"多个子路径的点被拼成一条假线"）；
③ 面积阈值从 400 降到 **200** —— 这个值是**量出来的**：全图 127 个闭合多边形的面积在这条线两侧是空的
（电阻本体 103.7 / 4 个必须保留的；排针本体 311.0 / 必须剔除的；中间 [150,300) 一个都没有）；
④ 加了 `python tools\sch_trace.py selftest` 自检（20 项），把"本体确实被剔除"和
"运放输入/输出脚没被并起来"等关键性质锁住，以后改坏了会直接报红。
顺带把 SVG/BBOX 的来源改成"环境变量 > 仓库内 > 旧临时目录 > 从 PDF 自动生成"，
不再依赖那个会消失的临时目录（验证过：重新生成的 SVG 与原来字节数完全相同，自检结果一致）。

> 另一个容易被误当成 bug 的现象：`net MA0_OUT` 会把 `MB0_OUT`/`MC0_OUT` 的 20k 分压一起报出来。
> 那是**真实的共地**（三路 20k 的下端拧在一起接 GND），不是工具错。已在工具文档里写明。

**(2) 由此产生的一条错结论扩散进了四份文档 + 代码注释。**
原结论："`MA0_OUT/MB0_OUT/MC0_OUT` 经 3kΩ → U1 的 TIM4_CH3/CH2/CH1"（电机输出端有定时器捕获通路）。
实际（用文字坐标逐脚复核）：

| 网络 | 实际到哪 | 经什么 |
|---|---|---|
| `TIM4_CH1/2/3` | **编码器座 CN2** 的 pin4/3/2，**U1 和 U2 都接**（PB6/PB7/PB8） | 3kΩ **上拉** 3.3V + SMF3.3A 对地 |
| `MA0_OUT/MB0_OUT/MC0_OUT` | **只到 ADC**（U1 IN8/IN7/IN6、U2 IN4/IN3/IN2） | 140k 串 + 20k 并（k=0.125）→ 缓冲 → 100Ω+1nF+TVS。**无定时器通路** |
| `MA_IN/MB_IN/MC_IN` | **U1 和 U2 都接**（PB5/PB4/PA8 = TIM3_CH2/CH1、TIM1_CH1） | **无任何元件** |

**复核方法**（两条独立证据，都不依赖那个有 bug 的代码路径）：
① 文字坐标计数 —— `docs/_extract/原理图文字坐标.txt` 里一个网络有几个别名就有几条引出线。
`TIM4_CH1/2/3` 恰好在三处出现（x≈221=U1 脚标签区、x≈528=U2 脚标签区、x≈1371=编码器块），
而 `MA0_OUT` 只出现在 x≈1191~1250（P1 端子+分压块），从不靠近任何 MCU 脚；
② `sch_trace.py dump <矩形>`（把窗口内线段原样列出，不受闭合判定影响）确认导线上没有元件符号。

**后果与修法**：

1. **`0x000F` 的两端对比没有物理意义** —— 现在是拿"U1 采编码器线"和"U2 采驱动信号"互判一致。
   要改成**两片测同一组（MA_IN 组）**，像 9 路 ADC 那样做真冗余互比。
   算法/线格式/ARM 窗口/45B 布局都不用动，只改 `pulse_cfg.c` 的相位↔通道绑定（方案见 `docs/12` §10）。
   **代码尚未改。**
2. **④ 电机三相输出检测不能走 TIM 捕获**，只能走 ADC 相电压。
   于是 ③④ 的联系是 `V_相电压平均值 ≈ 占空比 D × 母线电压`（比"两端周期一致"信息量更大）。
3. **治具唯一能向外驱动信号的引脚是 CN2 的 A/B/Z（经 U1 的 TIM4）。**
   其余接板外的脚全是输入；空闲脚（U1 的 PC13/14/15、PB1、PA15、PB3 等）在图上都是
   **叉形未连接标记、没有铜箔**。这条决定了 ⑤ 可行、⑥"治具注入"要另外飞线。
   > （**2026-10-27 新版原理图**之后多了一组对外驱动脚：**PA13/PA14** 被独立引出去给 DUT 做 SWD 烧录，
   > 所以"唯一能对外驱动的引脚"这句话现在要读成"CN2 的 A/B/Z **与** PA13/PA14"；见 §7.35。）
4. **撤回 Q6**（"MA0_OUT 可能直冲 MCU 引脚 >3.6V"）：那组 3kΩ 是编码器上拉，
   相电压那一路有 140k/20k 分压，24 V → 3.0 V，安全。
5. **`docs/06` 的两条结论要改**："每个通道后面都有 100Ω+1nF+TVS" → 只有 6 路相电压有。

**已更正的文档**：`docs/00`（§3.5 重写 + §3.6 复现方法）、`docs/04`（Q6 撤销 + 新增 Q7 + §7.2 接线）、

**教训**：**工具的输出不能当证据，工具本身也要被检。**
`docs/06` 里那句"所以'某网络接哪个引脚'是查出来的，不是猜的"当时是自信过头了 ——
它只对"孤立导线簇"成立，一旦查询涉及 IC/座子本体就会把整颗芯片并成一块。

> 补充一条**同样重要**的教训：`net MA0_OUT` 会把 `MB0_OUT`/`MC0_OUT` 的两路一起报出来，
> 一度被当成"工具又错了"。查下去发现是**真实的共地**（三路 20k 下端接同一个 GND）。

### 14.2 CubeMX 再生成是否会关掉 SWD：用 U2 工程实证

我早先把 `U1.ioc` 从 No Debug 改成 Serial Wire（否则再生成会写回

**实证**：同工程的 `U2` 就是 Serial Wire 配置，它的 `stm32f1xx_hal_msp.c` 里是：

### A.1 ISP 实现要点（源码已删除，仅备查）

- **协议**：AN3155 系统 bootloader。`0x7F` 同步 → 读版本 `0x01` → 全片擦除 → 逐 256B 块写 `0x31`
  → （可选）回读 `0x11` → 跳转 `0x21`。
- **擦除**：`0x43`/`0x44` 运行时自适应（按读回的 bootloader 版本决定先试哪个），载荷 `FF FF 00`。
- **写内存**：长度字节 `N-1` + 数据 + 校验和（`N-1` 与全部数据字节的 XOR）；
  **长度统一补齐到 8 字节**——8 是 4 的倍数，同时满足 F1(4) 与 G0(8) 的对齐要求，**无需知道被烧板型号**。
  仿真器按这两套规则各跑一遍均为零对齐违规（用例 T7b）。
- **串口**：ISP 期间 8E1（bootloader 要求），Go 之后切回 8N1（应用运行态）；
  **失败路径同样切回 8N1 并放开 BOOT0**（见 §7.11）。
- **非阻塞**：`ISP_Step()` 每次只推进一步（一次握手 / 擦除 / 一个 256B 块 / 一次回读），不长时间独占主循环。
- **回读校验**（`ISP_VERIFY_ENABLED`，**默认关闭**）：每写完一段逐 256B 回读与源镜像 `memcmp`，
  不一致报 `ERR_PROG` 且不执行 Go。
  > 默认关闭的原因：回读时序在不同 bootloader 版本上略有差异，**格式若与实际器件不符，
  > 一次成功的烧录也会被判为 ERR_PROG**。bring-up 确认可用后再打开（改一个宏）。
  > 已用 armcc 单独验证该分支在**目标编译器**下也能干净编译。
- **调试日志**：关键节点打到 USART1（PA9/PA10，4P 排针）115200 8N1：
  `[ISP] target BL ver=0x??` / `sync FAIL` / `erase FAIL` / `image head invalid, ABORT before erase` / `verify: DATA MISMATCH`。

### A.2 参考测径治具核对了什么（ISP 时代的 BOOT0/RESET 做法）

`diameter_JIG/U1/U1project/Core/Inc/isp_programmer.h`：

```c
#define U4_BOOT0_HIGH()  HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8,  GPIO_PIN_SET)
#define U4_BOOT0_LOW()   HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8,  GPIO_PIN_RESET)
#define U4_RESET_HIGH()  HAL_GPIO_WritePin(GPIOB, GPIO_PIN_15, GPIO_PIN_SET)
#define U4_RESET_LOW()   HAL_GPIO_WritePin(GPIOB, GPIO_PIN_15, GPIO_PIN_RESET)
```

进 bootloader 时序：

```
BOOT0 = H  →  RESET 拉低  →  10ms  →  RESET 拉高  →  50ms  →  发 0x7F  →  等 ACK
```

**本工程的 `ISP_ST_CONNECT()` 与之一致**，无需改动。两点差异是**刻意**的：

1. 测径治具用 PA8/PB15；本板 PA8 = TIM1_CH1、PB15 = SPI2_MOSI（接 U10），**已被占用**，
   故改用同样空闲的 **PB1 / PC13**；
2. 本工程在 Go 之后把 BOOT0 拉回低电平（参考实现保持高电平），这样被烧板下次上电能从应用正常启动。
