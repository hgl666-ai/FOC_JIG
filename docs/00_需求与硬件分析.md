## 1. 目标

做 FOC 烧录治具，**做到能正常烧录**。即：

```
PC ──USB CDC──▶ 治具 U1 ──SPI2──▶ GD25Q128 (16MB, 固件仓库)
                     │
                     ├──SWD 两线──▶ 被烧 FOC 板 MCU ──▶ 运行新固件
                     └──USART3────▶ U2（测量副控：9 路 ADC + 三相脉冲捕获）
```

## 2. 协议（从 xlsx 逐格提取）

### 2.1 单帧结构（最低 10 字节）

| 字段 | 帧头 F | 命令 C | 帧序号 N | 数据长度 L | 数据 D | CRC16 |
|---|---|---|---|---|---|---|
| 字节数 | 2 | 2 | 2 | 2 | * | 2 |
| 数据类型 | A5 5B | uint16_t | uint16_t | uint16_t | * | uint16_t |

- **字节序**：所有数据 **大端序**（高字节在前，低字节在后）。
- **波特率**：460800（xlsx 原文；实际链路见 §4 待确认项 Q1）。
- **帧头 F**：固定 `0xA5 0x5B`。
- **命令 C**：从 `0x01` 开始，`0x00` 不使用。
- **帧序号 N**：从 `0x01` 起递增的 u16，到 `0xFFFF` 后回卷到 1；**序号 0 特殊对待**。
  - PC 发一帧，治具处理后回 ACK，**ACK 的序号与收到的序号相同**。
  - 治具主动发的帧（除 ACK 外）序号一律为 **0**，便于 PC 区分 ACK 与主动报文。
- **数据长度 L**：u16，表示 D 的字节数。
- **CRC16**：MODBUS/CRC16，**从「帧头 F」到「数据 D」全部参与计算**，CRC 本身按大端存放。

帧结构字节布局：

```
偏移  0    1    2    3    4    5    6    7    8 .. 8+L-1   8+L   9+L
     A5   5B  CMD_H CMD_L SEQ_H SEQ_L LEN_H LEN_L  DATA...   CRC_H CRC_L
```

| 功能 | 发送方 | 命令 | 帧序号 | 数据长度 | 数据 D | 备注 |
|---|---|---|---|---|---|---|
| 固件 起始帧 | PC | `0x0009` | N | 9 | 2B u16 总帧数 + 4B u32 文件大小 + 3B 版本号 | PC 端向治具发送 FOC 板的固件 |
| 固件 起始帧 ACK | 治具 | `0x0009` | N | 1 | 1B u8 错误码 | |
| 固件 数据帧 | PC | `0x000A` | N | L | L 字节 u8：OTA 固件数据 | |
| 固件 数据帧 ACK | 治具 | `0x000A` | N | 1 | 1B u8 错误码 | |
| 固件 结束帧 | PC | `0x000B` | N | 0 | / | |
| 固件 结束帧 ACK | 治具 | `0x000B` | N | 1 | 1B u8 状态码 | |
| 烧录 Flash 固件到 FOC 板 | PC | `0x0112` | N | 0 | / | |
| 烧录 Flash 固件 ACK | 治具 | `0x0112` | N | 1 | 1B u8 状态码 | **ACK 在烧录完成后才返回**，`00` 成功 |
| 查询固件版本号（Flash 中） | PC | `0x000C` | N | 0 | / | |
| 查询固件版本号 ACK | 治具 | `0x000C` | N | 4 | 1B u8 状态码 + 3B u8 [主]:[次]:[修订] | 状态码：`0x00` OK / `0x06` ERR_NO_FW / `0x07` ERR_INCOMPLETE |
| 查询固件版本号（FOC 板中） | PC | `0x000D` | N | 0 | / | |
| 查询固件版本号 ACK | 治具 | `0x000D` | N | 4 | 1B u8 状态码 + 3B u8 [主]:[次]:[修订] | 状态码：`0x00`=成功, `0x0C`=失败（失败时版本号 `00 FF FF`） |

> 注：xlsx 中「命令 C」共 2 字节。表中 `0A/0B/0C/0D` 是高字节为 `00` 的两字节命令。
>
> **⚠ 修正记录（第 7 轮，用户确认）**：`0x0112`（烧录 Flash 固件到 FOC 板）最初被误读成 `0x0070`。
> 原因是 xlsx 里这个单元格存的是**数值 `112`**，我按十六进制理解成了 `0x70`；正确值应为 **`0x0112`**，
> 这也与测径治具的 PROGRAM 命令码一致。其余命令在 xlsx 里是共享字符串（`"0A"`/`"0B"`/`"0C"`/`"0D"`）
> 或数值 `9`（= `0x09`），不存在同类歧义。

### 2.3 通用状态码（Sheet1）

| 代码 | 名称 | 备注 |
|---|---|---|
| `0x00` | OK | 成功 |
| `0x01` | BUSY | 系统忙（非 IDLE 收到命令） |
| `0x02` | ERR_SIZE | 文件大小异常（为 0/越界/帧数 0/格式不对） |
| `0x03` | ERR_FLASH | SPI Flash 读写失败 |
| `0x04` | ERR_PROG | U4 ISP 烧录失败 |
| `0x05` | ERR_TEST | 治具测试失败 |
| `0x06` | ERR_NO_FW | 固件不存在（大小为 0 或越界） |
| `0x07` | ERR_INCOMPLETE | 固件不完整（完整标志缺失） |
| `0x08` | ERR_CRC | 帧 CRC 错误（仅诊断，不回 ACK） |
| `0x09` | ERR_SEQ | 帧序号非递增（仅警告，不拒绝） |
| `0x0A` | ERR_COUNT | 上传字节数与声明不符 |
| `0x0B` | ERR_PARAM | 参数错误 |
| `0x0C` | ERR_TIMEOUT | 上传超时（10s 无新数据） |
| `0x0D` | ERR_OVERFLOW | 上传溢出（超出声明大小） |
| `0xFF` | NIY | 命令未实现 |

### 2.4 完整时序

```
PC                                    治具 U1
──                                     ───────
0x0009 (总帧数, 文件大小, 版本号) ───▶ 选槽 → 解保护 → 擦扇区 → 写头部 → UPLOADING
                    ◀────────────────  ACK 0x0009 [00]

0x000A (≤N 字节固件数据) ────────────▶ 攒满 256B → 页编程
                    ◀────────────────  ACK 0x000A [00]
        …重复…

0x000B (无数据) ─────────────────────▶ 刷残页 → 比对字节数 → 写完整标志 0xA5 → 切槽 → IDLE
                    ◀────────────────  ACK 0x000B [00]

0x000C ──────────────────────────────▶ 读 Flash 头部
                    ◀────────────────  ACK 0x000C [状态][主][次][修订]

0x0112 ──────────────────────────────▶ SWD：连上目标 → 停内核 → 按扇区擦除
                                             → 写 Slot0(Bootloader) → 写 Slot1(App) → 回读校验 → 复位运行
                    ◀────────────────  ACK 0x0112 [状态]   ← 烧录完成后才回

0x000D ──────────────────────────────▶ SWD 直接读目标 App 分区里的版本号
                    ◀────────────────  ACK 0x000D [状态][主][次][修订]
```

### 3.5 测量通路（供后续测试功能用）

> ⚠ **本节 2026-10 重写过一次，因为原版有实质性错误。**
> 原版把 `PB6/PB7/PB8` 上那组「3kΩ + SMF3.3A」误算到了 `MA0_OUT/MB0_OUT/MC0_OUT` 头上，
> 由此得出"电机输出端有定时器捕获通路"的结论 —— **是错的**。
> 根因：追踪脚本 `tools/sch_trace.py` 判多边形闭合用 `d.strip().endswith('Z')`，
> 而 pdftocairo 把一个闭合矩形写成 `M x0 y0 L … L x0 y1 Z M x0 y0` ——
> **闭合的 `Z` 后面还跟着一个"只有 moveto 的空子路径"**，字符串末尾是 `M x0 y0` 而不是 `Z`，
> 所以 `endswith('Z')` 恒为 False，"剔除 IC/座子本体"那段代码**从未生效**（2026-10 已修，见下）。
> 后果：一颗 48 脚 IC 的全部引脚会通过本体外框在几何上连通成一块
> （`net U1-RX1` 返回 178 段、把 VBAT/VDD_3/48 个脚号全拉进来就是证据）。
> 下面这一版按**文字坐标逐脚核对**重做（方法见 §3.6），不依赖那个工具。

| 信号 | 从哪来 | 经什么 | 到哪 |
|---|---|---|---|
| 24V 母线 | 被测板（图上标"被测点输入"） | 32.4k 串 + 4.7k 并（k≈0.1267）→ 缓冲 | U1 **IN5** / U2 **IN5** |
| 10V 驱动供电 | 被测板 | 同上（k≈0.1267） | U1 **IN4** / U2 **IN6** |
| 5V 电源 | 被测板 | 20k 串 + 30k 并（k=0.6） | U1 **IN0** / U2 **IN1** |
| 3.3V 电源 | 被测板 | 3k 串 + 30k 并（k≈0.909） | U1 **IN1** / U2 **IN0** |
| A/B/C 相输出对功率地 | 被测板，经 **P1 接线端子**（脚 3/2/1）+ 测试点 | 140k 串 + 20k 并（**k=0.125**）→ 缓冲 → 100Ω+1nF+SMF3.3A | U1 **IN8/IN7/IN6**、U2 **IN4/IN3/IN2** |
| 电流检测 1/2 | 被测板电流采样放大器的**输出**，经「双相电流测试点接口」的 2 个测试点 | **直连**（只 + 对地 SMF3.3A，无串阻、无分压）→ 缓冲 | U1 **IN2/IN3**、U2 **IN8/IN7** |
| 主控驱动信号 MA_IN/MB_IN/MC_IN | 被测板 MCU 的 PWM 输出（栅极驱动**之前**） | **路径上无任何元件**（无串阻/无分压/无钳位） | **U1 和 U2 都接**：PB5/TIM3_CH2、PB4/TIM3_CH1、PA8/TIM1_CH1 |
| 编码器 A/B/Z | **CN2**（XH-5PA，5 脚：5V / A / B / Z / GND） | 3kΩ **上拉到 3.3V** + SMF3.3A 对地 | **U1 和 U2 都接**：PB8/PB7/PB6 = TIM4_CH3/CH2/CH1 |

**四条会直接影响测试方案的更正（别漏读）**

1. **`MA0_OUT/MB0_OUT/MC0_OUT` 没有任何定时器通路**，只到 ADC（上表第 5 行）。
   所以"用 TIM 捕获测电机输出端的周期/占空比"**在这块板上做不到**。
   唯一变通：U1 的 `PA6/PA7/PB0` 恰好也是 `TIM3_CH1/CH2/CH3` 的复用脚，
   把这三个脚从 ADC 改成输入捕获就能测周期 —— 代价是 U1 失去三相电压读数，**当前决定不做**。
2. **`PB6/PB7/PB8` 不是"电机输出端"，是编码器座 CN2 的三个信号脚。**
   那组 3kΩ 是**上拉到 3.3V**（编码器集电极开路输出的典型接法），不是串阻。
   因此 `docs/12` 里"MA0_OUT 是 24V 级信号可能直冲 MCU 引脚（>3.6V）"那条风险**不成立，已撤回**
   （真正的相电压那一路有 140k/20k 分压，24V → 3.0V，安全）。
3. **`MA_IN/MB_IN/MC_IN` 和编码器 A/B/Z 这两组信号，U1 与 U2 都挂在同一条线上。**
   这正好让"一片驱动、另一片采集"的回环测试成为可能。
4. **治具唯一能对外驱动的逻辑信号，是 CN2 的 A/B/Z（经 U1 的 TIM4_CH1/2/3）与 PA13/PA14**
   —— 后两者是 2026-10-27 新版治具原理图独立引出去给 DUT 做 **SWD 烧录**的两脚（网络 `U1-SWD`/`U1-SCLK`，
   即 U1 自己的 SWD 口，见 `docs/09` §2）；**其余接板外的脚全是输入。**
   原理图上**没有被引到排针/测试点的空闲脚**：U1 的 PC13/14/15、PB1、PA15、PB3 与 U2 的另外 6 个脚，
   在图上都是**叉形未连接标记、没有铜箔**（图上没有"空闲"二字，未用脚就是这个记号）。
   ⚠ PA15/PB3/PB4 是 U1 自己的 JTAG 脚（JTDI/JTDO/NJTRST）：生产固件 `SWJ_CFG=100` 时它们**一并变成普通 IO**
   （其中 PB4 = TIM3_CH1 已被 ③ 用作 B 相捕获）；开发版（`SWD_FREE_DEBUG_PINS=0`）里它们仍归 JTAG/SW-DP。

> 遗留不确定项：`U1_ADC1_IN3` 那个文字标签的落点离 U5 的 VCC 线只有 3.6pt、离它的 2OUT 输出线 5.1pt，
> 仅凭 PDF 几何不能 100% 排除"印在 5V 线上"的排版错误，其余 17 路无此问题。
> 建议在 EDA 源文件里核一下这个标签的锚点。

### 3.6 这一版是怎么核出来的（可复现）

不用 `sch_trace.py` 的 `net/batch/at`（受上面那个闭合判定 bug 影响），改用两条独立证据：

1. **文字坐标计数**：`docs/_extract/原理图文字坐标.txt` 里每个网络别名的 (x,y) 都记着，
   一个网络有几处别名 = 它有几条引出线。例如 `TIM4_CH1/2/3` 恰好出现在三处
   （x≈221 = U1 脚标签区、x≈528 = U2 脚标签区、x≈1371 = 编码器接口块），
   证明这**三根线各把 U1、U2、CN2 连在一起**；而 `MA0_OUT` 只出现在 x≈1191~1250
   （P1 端子 + 分压块），**从不靠近任何 MCU 脚**。
2. **原始线段**：`python tools\sch_trace.py dump <x0> <y0> <x1> <y1>`（`dump` 只是把窗口内的
   线段原样列出来，不受闭合判定 bug 影响），用来确认某段导线上**有没有**电阻/电容/二极管符号。

## 5. 待确认问题（阻塞项）

### Q1 — PC↔治具 链路 ✅ 已确认
**USB CDC 虚拟串口**（U1 PA11/PA12 → USB-B 座）。
xlsx 中的「460800」按形式参数处理，不作波特率配置依据。

### Q2 — 0x0112 烧录被烧板的物理链路 ✅ **改用 SWD 两线（已实现）**

用户第 7 轮确认的架构：原理图这块板就是**治具**（U1 主控 + U2 副控），
**被烧 MCU 是到时候外接的另一块板**（设计号不是 U1）；治具板上有**外部 SPI Flash 存放被烧固件**
（= U10 GD25Q128 @ SPI2/PB12，已按此实现）。

第 15 轮把烧录通道从 **UART ISP（AN3155 + BOOT0/RESET）** 换成了 **SWD 两线**：

| 项 | 现在是什么 |
|---|---|
| 物理链路 | SWCLK + SWDIO + GND；**不用 BOOT0、不用 RESET** |
| SWD 引脚 | **SWCLK = PA14**（网络 `U1-SCLK`）/ **SWDIO = PA13**（网络 `U1-SWD`），2026-10-27 新版治具原理图确认；`swd_config.h` 里 `SWD_PINS_CONFIRMED = 1`。这两个就是 **U1 自己的 SWD 口**，新版板独立引出去烧 DUT，所以**生产固件会关掉 SW-DP**（`SWJ_CFG=100`，见 `docs/09` §2.1） |
| 为什么换 | ISP 要占 USART3 + 两根控制线，而 USART3 现在是 U1↔U2 的内部链路；SWD 只要两根线、不占串口 |
| 目标识别 | 读 SW-DP IDCODE `0x2BA01477` / DEV_ID `0x413`，被烧板型号不用再猜 |
| 双镜像地址 | Bootloader `0x08000000`+`0x10000`（64KB，扇区 0..3）、App `0x08010000`+`0x80000`（512KB，到 `0x08090000`）—— **已按 FOC 工程确认**；`DUT_GO_ADDR = 0x08000000`，`DUT_VER_OFFSET = 0x20` **仍是占位值** |

做法、时序与排查见 `docs/09_SWD烧录说明.md`。
### Q3 — 0x000D「查询固件版本号（被烧板中）」🟡 已改成直接读目标 Flash

不再依赖被烧板的串口协议：`0x000D` 现在**通过 SWD 直接读 App 分区里的版本号**
（偏移 `DUT_VER_OFFSET`，**当前是占位值 `0x20`**，等 FOC 工程确认）。
读不到时回 `06 ERR_NO_FW`（App 区是空的）或 `0C ERR_TIMEOUT`（连不上目标）。
### Q4 — U1 自身固件版本号
协议 `0x000C` 回的是 Flash 里被烧板的固件版本，但**没有**协议查询 U1 自身版本；
本项目是否需要沿用测径治具的 `0x0004`「查询 U1 版本」？（xlsx 未列出）
