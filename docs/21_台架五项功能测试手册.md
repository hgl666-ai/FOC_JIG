# 21 台架五项功能测试手册（被测 FOC 板）

> **面向操作者**：照着这一份从上往下做，每一步都有"发什么、期望是什么、不对怎么办"。
> 协议细节在 `docs/17`（PC 命令清单）/ `docs/15`（DUT 协议规格），这里只讲**怎么测**。
>
> **建立日期**：2026-11-04。适用固件：Keil target **`U1_DUT`**（`U1/MDK-ARM/U1_DUT/U1_DUT.hex`）。

---

## 0. 一句话：今天为什么能测，靠的是什么

五项功能（① 电压 / ② MCU 脉冲 / ③ 三相输出 / ④ 编码器 / ⑤ 相电流）**每一条都要和被测 FOC 板说话**，
所以治具必须同时有两个串口：一个接 PC、一个接被测板。U1 只有两路可用串口
（USART1 = PA9/PA10，USART3 = PB10/PB11；USART2 的 PA2/PA3 是 A/B 相测量，挪不动），
于是台架形态这样分：

```
        ┌──────────────┐   USART1 (PA9/PA10)   ┌────────────┐
        │ PC / USB-TTL │◄────────────────────►│            │
        └──────────────┘   115200 8N1         │  治具 U1   │
                                              │  C8T6      │
        ┌──────────────┐   USART3 (PB10/PB11) │            │
        │ 被测 FOC 板  │◄────────────────────►│            │
        └──────────────┘   (H3/H4 跳线位置)   └────────────┘
                                                   ▲
                           U2 从内部链路脱离（H3/H4 拔掉）→ 交叉校验退化为单片判定
```

| 项 | 台架形态（现在） | 出厂形态（USB 修好后就是它） |
|---|---|---|
| PC 口 | **USART1**，USB-TTL | USB CDC（虚拟串口） |
| 被测板口 | **USART3**（H3/H4 拔掉后那两颗针） | USART1 |
| U2 | **不参与**（`JIG_U2_LINK=0`） | USART3 |
| Keil target | **`U1_DUT`** | `U1` |
| 能不能烧录 | ❌ **不能**（用它上传固件会失败，见 §7.1） | ✅ 烧录 + 五项功能都在这一份固件里 |

> **产品只有一台治具、一份固件**：`U1`（USB 出厂版）从 2026-11-05 起已经同时包含
> 烧录（SWD 写 FOC 板）和 ①~⑤ 五项测试，Flash 47716/65536、RAM 14344/20480。
> 下表这个“台架形态”只是 **USB 那对 D+/D- 还没修好** 期间的旁路，
> 目的是先用 USART1 当 PC 口把五项功能验通；USB 一恢复就应该只在 `U1` 上工作。

**代价（只影响治具自检，不影响被测板那五项）**：
`0x000E / 0x000F` 的交叉校验块恒无对侧数据（`NO_PEER` 置 1、不判失败）；`0x0013` 直接回超时；
④ 编码器退化成"预期边沿数 vs 被测板自己数的"。这些都写进了 `jig_mode.h §3.4.1`。

## 1. 开测前的接线核对（逐条打勾）

| # | 项 | 要求 | ☐ |
|---|---|---|---|
| 1 | 治具 U1 固件 | 烧的是 **`U1_DUT.hex`**（用你原来的 UART1 ISP 流程：H1/BOOT0 拉高 → 复位 → 用 USART1 烧 → BOOT0 拨回 → 复位） | ☐ |
| 2 | PC ↔ 治具 | USB-TTL：**TXD→治具 PA10、RXD→治具 PA9**、GND 共地，115200 8N1 无流控 | ☐ |
| 3 | 治具 ↔ 被测板 | **治具 PB10 → 被测板 RX（USART 的 RX）**、**治具 PB11 → 被测板 TX**（交叉）、**共地** | ☐ |
| 4 | H3/H4 跳线 | **拔掉**（U2 脱离内部链路，把 PB10/PB11 让给被测板） | ☐ |
| 5 | 被测板供电 | 逻辑电必须有；**动力电（24V）先按 §2 的规矩决定开不开** | ☐ |
| 6 | 三相电机 | 已接 A/B/C（③ 会用到；⑤ 有电流流过它，见 §2） | ☐ |
| 7 | COM 号 | 设备管理器里记下 USB-TTL 的号（下文用 `COM7` 举例） | ☐ |

> ⚠ **只有 3 根线要接**（TX、RX、GND）。**别把 3.3V 从治具接给被测板**：
> 两块板各自有供电，接 3.3V 会把两路 LDO 顶在一起。

## 2. 安全红线（请先读完再上电）

| 场景 | 红线 |
|---|---|
| ③ 三相输出 | **三相占空比必须相同**（本手册全是 50%）。三相同占空比 → 线间电压为 0 → 电机不转、不过流。**一旦三相不同**，24V 就横加在两个绕组上 |
| ⑤ 相电流 | **绝不用 `--curmode 0`（静态全通）**。静态模式被测板按 1000‰ 处理、**忽略占空比**，等于 24V 直接压两个绕组；绕组 0.1~1Ω 时是 24~240A。本手册默认 `--curmode 1` + 20‰ + 100ms |
| 通流时的姿势 | 手放在**动力电源开关**上；闻到味道/听到异响 → 立刻断电 |
| 任何一项异常 | 先发 `python tools\foc_jig_tool.py -p COM7 raw A5 5B 00 11 00 01 00 02 02 03 XX XX` 或直接断电。治具每项测试结束都会自动发 `DUT_STOP` 关输出 |
| 被测板看门狗 | 被测板固件必须实现失联看门狗（`docs/16 §3`）。治具侧每条流程结束也会发 STOP，但**看门狗是最后一道保险** |

## 3. 测试顺序（这就是要照着做的顺序）

顺序不是我随便排的，按"**先证明链路 → 再测只读的 → 再测输出但不过流的 → 最后测过流的**"来：

| 步 | 测什么 | 命令 | 风险 | 为什么排这个位置 |
|---|---|---|---|---|
| 0 | 固件是不是台架版 | `0x0017` | 无 | 5 秒确认"我烧的固件对不对"，否则后面全是假的 |
| **0.5** | **串口线通不通（不用协议）** | **`0x001F` 发 `AS:S800` / `AS:S0`** | 低（电机会真转） | FOC 固件没实现 `0x02xx` 之前，第 1 步必然回 `0C`；先用对面的 ASCII 命令把"线通不通"证掉，才能区分"线坏"和"对面没实现协议" |
| 1 | **DUT 链路通不通 / 被测板有没有实现协议** | `0x0011` 透传 PING | 无 | **一切的前提**。不通就停在这里，别浪费时间 |
| 2 | 被测板功能声明与 ADC 通道 | `0x0011` INFO | 无 | 决定后面哪几项**能测**、哪几项被测板根本没实现 |
| 3 | **① 电压检测** | `0x0015` | 无（只读） | 最安全，而且**最能暴露接线错**：24V/5V/3.3V 一读就知道板子对不对 |
| 4 | **② MCU 脉冲检测** | `0x0019` | 低（三相同占空比，无净电压） | 验证"被测板 MCU 的 PWM 有没有出来、频率占空比对不对" |
| 5 | **③ 三相输出检测** | `0x001A` | 低（同上） | 验证"驱动级有没有把 PWM 变成电压"（V ≈ 占空比 × 母线） |
| 6 | **④ 编码器检测** | `0x001B` | 无输出（只发 A/B/Z 逻辑脉冲） | 和功率级无关，什么时候都能测 |
| 7 | **⑤ 相电流检测** | `0x0014` | **中（真有电流）** | 唯一会让电机里过电流的一项，放最后 |
| 8 | 一键全跑（产线用） | `0x0010` | 同 3~7 | 前面每一项都单独通过之后，再验证"一条命令跑完" |

> 下文每条命令都在 **`D:\Project\FOC_JIG`** 目录下执行；
> python 用你自己的（`python` 或 `D:\Develop\python\python.exe`），下文的 `python` 请自行替换。

### 第 0 步　确认烧进去的是台架版固件

```
python tools\foc_jig_tool.py -p COM7 status
```

**期望**（关键就一行）：
```
  标志 = 0x08（U2不在 **DUT链路已编入**）
```

| 现象 | 含义 | 处理 |
|---|---|---|
| `没有DUT链路(固件不是U1_DUT)` | 烧的还是 `U1_UART` 版 | 重烧 `U1/MDK-ARM/U1_DUT/U1_DUT.hex` |
| 完全没应答 | 串口/波特率/固件没跑 | 先确认 `0x000C` 那种最简查询也不通，按 §5.1 查 |

### 第 0.5 步　先用 `AS:` 命令验通 USART3 ↔ FOC 板（**不等 0x02xx 协议**）

> **适用场景**：FOC 板固件还没实现 `docs/22` 那套帧协议，但它已经能认两条 ASCII 命令：
> **`AS:S800` = 电机转**、**`AS:S0` = 电机停**。先用这两条把"线通不通"这件事确认掉。

**先确认治具这版有这两条命令**（`0x001F` / `0x0020`，`U1_DUT` 与 `U1` 都编进去了）：

```
python tools\foc_jig_tool.py -p COM7 as-start
```

**看到什么算什么**：

| 工具输出 | 结论 | 下一步 |
|---|---|---|
| `✅ 双向都通：发出去了，对端回了 N 字节` | 收发都通 | 直接进第 1 步（`dut-ping` 会回 `0C`，正常） |
| `字节已经发出去了，但对端一个字节都没回` + **电机转了** | **通了**（对面不回应答而已） | 马上 `as-stop` 停下，记下这个事实 |
| `字节已经发出去了…` + 电机没动 | 治具发出去了，但对面没执行：查 **TX 有没有接到它的 RX**、共地、波特率 | 见下表 |
| `只写出去 N/M 字节` | 治具发送队列忙 | 重发一次 |
| 工具报"治具没发出去" | 上一条还在发 | 重发一次 |
| **没应答**（连治具都不回） | PC↔治具这一路的问题，与 FOC 板无关 | 见 §5.1 |

停：
```
python tools\foc_jig_tool.py -p COM7 as-stop
```

再看一眼它有没有吐过东西（读后清空）：
```
python tools\foc_jig_tool.py -p COM7 dut-recv
```

**为什么要单独有这一步**：`dut-ping`（第 1 步）要求对面**认帧协议**，FOC 固件没做好之前必然回 `0C`。
但那时的 `0C` 分不清"线没通"和"对面没实现协议"—— 这两件事的处理方式完全不同。
`as-start` 用**不需要协议**的方式把线先证一遍：字节真到了对面、对面真的动了，这条线就是通的。

> ⚠ **安全**：`as-start` 会让电机真的转起来（对面收到就执行）。第一次试把占空比留小、
> 或者先脱开负载；手放在动力电源开关上。停用 `as-stop`。
>
> ⚠ 这条命令**不会自动重试**（重发会把 `AS:S800` 执行两遍）。

**工具超时/等待时间**：默认等 200ms 回字，可调：
```
python tools\foc_jig_tool.py -p COM7 as-send AS:S800 --tmo 500
```

### 第 1 步　DUT 链路 + 被测板协议（**这一步不过，后面全别做**）

```
python tools\foc_jig_tool.py -p COM7 dut-ping
```

**期望**：
```
→ 0x0011 透传 0x0200 PING，DATA=DE AD BE EF
  治具状态 = OK
  被测板回显 = DE AD BE EF
  ✅ 完全一致 —— **DUT 链路通了，被测板固件实现了 DUT 协议**
```

**如果不是这样**，按这个顺序排（`dut-ping` 会直接把下面几条印出来）：

1. **`治具状态 = ERR_TIMEOUT (0C)`** → 治具发了、**被测板没回**。三种可能：
   - 被测板固件里**没有** `0x0200~0x0208` 这 9 条命令（最可能，见 `docs/16`）；
   - TX/RX 没交叉（治具 PB10 必须接被测板 **RX**）；
   - 没共地 / 被测板串口没初始化 / 波特率不是 115200。
2. **`治具状态 = ERR_PARAM (0B)`** → 透传命令号不在 `0x0200~0x02FF`，或内部链路正忙，重发一次。
3. **回显对不上** → 链路通了但被测板的 PING 不是"原样回显"，按 `docs/16 §2.1` 改。

> 想直接看被测板回了什么原始字节：
> `python tools\foc_jig_tool.py -p COM7 raw A5 5B 00 11 00 01 00 06 02 00 DE AD BE EF 6D 5B`

### 第 2 步　拿被测板的功能声明

```
python tools\foc_jig_tool.py -p COM7 dut-info
```

**期望**（举例：9 条全支持、9 路 ADC 全支持）：
```
  DUT 协议版本 = 0x0101（应为 0x0101）
  功能声明     = 0x03FF
     支持：PING, INFO, TEST_MODE, STOP, PWM, LEVEL, CURRENT, GET_ADC, GET_ENC
     PWM 频率范围 = 100 ~ 20000 Hz
     ADC 通道掩码 = 0x01FF → 24V 母线, 10V 驱动, 5V, 3.3V, A 相电压, B 相电压, C 相电压, 电流检测1, 电流检测2
  ⇒ 后面能测什么（按这份位图）：
     ① 电压检测   0x0015 : 可以（只要 GET_ADC 有通道）
     ② MCU 脉冲   0x0019 : 可以
     ...
```

**按这里的结论决定跳过哪几项**：被测板没声明的能力，对应那项测不了（不是治具的错）。

### 第 3 步　① 电压检测（只读，最安全）

```
python tools\foc_jig_tool.py -p COM7 vol
```

**期望**：一张 9 行的表（`测点 / 治具读到 / 被测板报的 / 差值 / 判定`），`24V 母线 / 10V 驱动 / 5V / 3.3V` 四行是**电源的实际电压**，
A/B/C 三相和两路电流按被测板有没有声明显示"合格"或"不判(数据缺)"。

**怎么判**：

| 现象 | 含义 |
|---|---|
| 24V 那行读到 23~25V | ✅ 母线分压、ADC、基准全对 |
| 24V 那行读 0V 但电源确实是 24V | ① 治具的分压/接线断；② 被测板根本没上动力电 |
| 治具和被测板读数差很多（"超差"） | 有一边的换算系数错了：相电压分压比是 **k=0.125**，两边都应按"信号侧 mV"报（`docs/16 §2.8`） |
| 九行全"不判(数据缺)" | 被测板 `INFO` 里 `adc_mask=0`（没实现 GET_ADC 或没声明通道） |

**这一项最值钱**：它同时验证了治具的 9 路 ADC、被测板的 ADC、以及"两边对同一个电压的理解一致"。

### 第 4 步　② MCU 脉冲检测（被测板 MCU 的 PWM）

```
python tools\foc_jig_tool.py -p COM7 pulse
```

治具会自动做：进测试模式 → 让被测板发 **1kHz / 50% / 300 个（300ms）** → 开 200ms 捕获窗口 → 关输出。

**期望**：
```
  对侧(U2)：没有对侧数据

  相   频率        占空比     判定
  A    1000.0 Hz   50.0%      有信号
     B   1000.0 Hz   500.0 us     500‰   200     0x00
     C   1000.0 Hz   500.0 us     500‰   200     0x00
```

| 现象 | 含义 | 处理 |
|---|---|---|
| 三相都是 `(无信号)` | 被测板没输出 PWM，或**脉冲线没接**（治具 PB5/PB4/PA8 ← MA_IN/MB_IN/MC_IN） | 先 `dut-info` 看 `PWM` 位；再看那三根线 |
| 只有某一相无信号 | 那一根线断/焊反 | 对调验证 |
| 频率不是 1kHz | 被测板 PWM 定时器配置不同 | 记录实际值，按实际改判据 |
| 占空比不是 500‰ | 被测板没按请求的 duty 输出 | 记录实际值；差太多是固件问题 |
| `判定 = ERR_TEST (05)` | 调试版 `PULSE_JUDGE_ENABLE=0` 时不会发生；产线版会 | 看上面哪一行不对 |

> 台架没有 U2 → 下面那块"对侧(U2 输入端)"全是 0，**正常，不参与判定**。

### 第 5 步　③ 三相输出检测（V ≈ 占空比 × 母线）

```
python tools\foc_jig_tool.py -p COM7 phase
```

**期望**（母线 24V、占空比 50%）：
```
  相   实测        期望(占空比×母线)   差值      判定
  A    12.120 V    12.000 V            +120      合格
  B   12.000 V          +60  1.200 V    500‰   0x01 合格
  C   12.000 V           +0  1.200 V    500‰   0x01 合格
```

**判据**：实测相电压（治具走 140k/20k 分压量到）应 ≈ 占空比 × 母线电压；容差是 `max(5%, 200mV)` 量级。

| 现象 | 含义 |
|---|---|
| 期望 12V，三相差值都在 ±1V 内 | ✅ 驱动级、分压、ADC 全对 |
| 期望 12V，但某相实测 ≈ 0 → "超差" | 那一相**没输出**：驱动芯片/自举电容/相线断 |
| 期望值也是 0 | 治具不知道母线电压（`0x0015` 里 24V 那路也应该是 0）→ 先修第 3 步 |
| 三相都是 0 但脉冲是好的 | 功率级没上电（24V 没接/没开）——**脉冲是对的、输出没电**，这个组合很典型 |

> ⚠ 别把三相占空比改成不一样来"看得更清楚"：那会让电机真的通流。要单独验某一相，用 `0x0016` 手动判据
> （`duty=0xFFFF` 的那一相按"高阻、不判"处理）。

### 第 6 步　④ 编码器检测

```
python tools\foc_jig_tool.py -p COM7 enc
```

治具会：进测试模式（被测板清计数）→ 从 CN2 的 A/B/Z 发脉冲 → 读被测板的计数 → 三方比对。

**期望**：
```
  相   被测板数到   应该是   判定
  A    2000        2000       合格
  B   4000       3998         0x01 合格
  C   2          2            0x01 合格
```
（默认脉冲串 A=1000@5kHz、B=2000@10kHz、Z=1；**一个方波 = 2 个边沿**）

| 现象 | 含义 |
|---|---|
| 三路都 ≈ 期望（允许几十个边沿的量化误差） | ✅ 编码器接口通、被测板计数语义对 |
| 某路 = 0 | 那根线没接 / 被测板没开那个输入 |
| A 和 B 的**个数互换了**（1000↔2000） | A/B 两根线接反（三路个数故意不同就是为了这个） |
| 都是期望的一半 | 被测板只数了单沿（固件问题，`docs/16 §2.9` 要求两种沿都数） |
| 全部 = 0 且 `被测板状态` 非 0 | 被测板没实现 `GET_ENC`（看 `dut-info` 的 `GET_ENC` 位） |

### 第 7 步　⑤ 相电流检测（**只有这一步真有电流**）

先用**最小占空比**试一次：

```
python tools\foc_jig_tool.py -p COM7 cur --duty 20 --ms 100
```

含义：上桥 A、下桥 B、20‰（2%）占空比、100ms、低频 PWM 模式。

**期望**：
```
  判定 = OK
  被测板状态 = OK
  路   治具变化量   被测板变化量   判定
  1    +10 mV       +12 mV         合格
```
判的是**变化量**（通流中 − 基线），零点偏置不用管。

| 现象 | 含义 | 下一步 |
|---|---|---|
| 变化量 0~几 mV | 电流太小，看不出来（正常） | 占空比往上加：`--duty 50` → `100` → `200`，每次看一眼变化量 |
| 变化量随占空比单调变大 | ✅ 采样链路通 | 记录"多大占空比对应多大 mV"，这是**换算成安培的标定数据** |
| 变化量一直是 0，且 `被测板状态 = 0B` | 被测板不认这个 `mode=1`（只实现了静态） | 只能等被测板固件补 PWM 模式；**不要**为了看数字改成 `--curmode 0` |
| `被测板状态 = 0C` | 被测板没应答 | 回第 1 步 |
| 两路读数全都一样且不变 | 治具的分流检测通道没接 | 查治具那两个电流检测点 |

> **为什么不能 `--curmode 0`**：静态模式被测板按 1000‰ 处理、忽略占空比，
> 等于 24V 直接加在两个绕组上。产线上"夹具提供电流回路"（串了限流电阻）才能这么干；
> 台架上接着电机就是短路。工具默认 `--curmode 1` 就是为了防这一下。

### 第 8 步　一键全流程（前面都过了再做）

```
python tools\foc_jig_tool.py -p COM7 run-all
```

12 步：进测试模式 → ①电压 → 发PWM → ②脉冲采集 → ③三相判定 → 再进测试模式 → ④清零 → 发脉冲 → 读U2 → 读被测板 → ⑤相电流 → 关输出。
**约 5~20 秒**，中途别拔线。

> ⚠ 一键流程里的 ⑤ 用的是**默认参数（静态全通 100%、200ms）**。
> **被测板接着电机时不要跑 `run-all`** —— 要跑就把电机脱开，或先把 `APP_RunStartStep` 里
> 第 10 步的参数改成小占空比（见 `app.c` 的 `APP_RUN_STEP_CUR`）。

## 4. 判读速查

| 状态码 | 在测试类命令里的含义 |
|---|---|
| `00 OK` | 测完了、**判定合格** |
| `05 ERR_TEST` | **测完了、判定不合格**（正常业务结果，**不是通讯错误**） |
| `01 BUSY` | 治具正忙（上一次没结束），等一下重发 |
| `0B ERR_PARAM` | 参数非法（如 `hi/lo` 同相、占空比越界、LEN 不对） |
| `0C ERR_TIMEOUT` | 等被测板应答超时 → 被测板没回 |
| `FF NIY` | 固件没有这条命令（没编 `JIG_DUT_LINK`） |

| 判定旗标（每路一位） | 含义 |
|---|---|
| `01` | 合格 |
| `02` | **数据不全 → 不判**（不是失败） |
| `04` | 没通流（⑤ 用） |
| `08` | 与对侧读数差超容差 = 真故障 |

## 5. 故障对照

### 5.1 连治具都连不上（任何命令都没应答，例如 `0x0017` 超时）

**先跑这三条定位命令**，按顺序，每条都能把一半的可能性排除掉：

| # | 命令 | 它回答什么问题 | 结论 |
|---|---|---|---|
| 1 | `python tools\foc_jig_tool.py -p COMx isp-probe` | 芯片**在不在**系统 bootloader 里 | 回 `0x79` = **应用根本没跑**（BOOT0/H1 还在高，或拨了没复位）；无应答 = 应用应该已经在跑 |
| 2 | `python tools\foc_jig_tool.py -p COMx probe` | 是不是**波特率**不对 | 某一档回帧 = 改 `-b` 用那一档；六档全无 = 不是波特率的事 |
| 3 | `python tools\foc_jig_tool.py -p COMx loopback` | **适配器/线/COM 号**好不好 | 短接适配器自己的 TXD-RXD 后收发一致 = 适配器没问题，嫌疑在治具那一段 |

然后是**只有现场才能确认的三件事**（按出现频率排）：

| 序 | 检查 | 怎么确认 | 典型症状 |
|---|---|---|---|
| 1 | **BOOT0（H1）有没有拨回 0，拨完有没有复位** | 用 `isp-probe`；或直接断电 → 拨回 BOOT0 → 再上电 | 烧完 ISP 就这么放着 → 芯片停在 bootloader，**对任何 0x00xx 帧都不理**，表现就是"完全没应答" |
| 2 | **USB-TTL 接的是哪两颗针** | 必须是 **PA9/PA10（USART1）**。台架形态下 **PB10/PB11（USART3）是被测板口**，接那儿当然收不到 PC 的帧 | 和"接被测板"那两个针搞混 —— 这版固件把 USART3 整段划给了 DUT，PC 帧进不去 |
| 3 | TXD/RXD 有没有**交叉**、有没有**共地** | 适配器 TXD → 治具 PA10；适配器 RXD → 治具 PA9 | 交叉接反：治具收不到；不共地：时好时坏 |

### 5.2 能连治具，但每个测试命令都回 `FF`

固件不是 `JIG_DUT_LINK=1` 的版本 → 重烧 `U1_DUT.hex`（第 0 步能直接看出来）。

### 5.3 万一还是不行：回退验证，把"固件"和"硬件"彻底分开

烧回 **`U1_UART.hex`**（那版是之前烧录功能验证过、确定能通的那一版），再发：

```
python tools\foc_jig_tool.py -p COMx query-flash
```

| 结果 | 说明 |
|---|---|
| 能回帧 | 硬件/接线/适配器**都是好的** → 问题在 `U1_DUT` 这一版固件，把 `status` 的原始字节发我 |
| 还是没应答 | 和固件无关，是**物理层**（BOOT0 / 接线 / 适配器 / COM 号）的问题 |

> 补充：`U1_DUT` 这版把调试打印关了（`BSP_DBG_ENABLE=0`，因为 USART1 归 PC），
> 所以上电时 **PA9 不会吐任何字符** —— 别用"串口助手看不到上电字符"来判断板子没跑。
> 想看它到底吐不吐，用 `watch`：U1_DUT 上电应该是**安静的**（0 字节），这是正常的。

### 5.3 `dut-ping` 回 `0C`（治具等不到被测板）

按这个顺序查：被测板固件有没有那 9 条命令 → TX/RX 交叉 → 共地 → 被测板串口初始化 → 波特率。

### 5.4 测得数字都不对，但链路是通的

先跑第 3 步（电压）：如果 24V/5V/3.3V 都对，说明治具的 ADC 和基准没问题，
问题在被测板报的数或换算系数（相电压分压比 k=0.125、电流是"信号侧 mV"）。

## 7. 已知问题（2026-11-05 实测记录，**按决定暂不修**）

### 7.1 每次新开工具，**第一条命令**会超时一次

**现象**：`status` 第一次 2 秒超时 → 工具自动重试（新 SEQ）→ 立刻成功。
心跳读数很稳定：`rx_bytes = 7 + 10 = 17`、`frames=1`、`stalls=1`、`tdrop=0`、`rearm=1`、`rxerr=1`。

**已查明的部分**：
- 重试那帧**完整收到并正确解析**，应答也正常发出（`txdrop=0`）→ **不影响功能正确性**；
- 第一帧只到 **7/10 字节**（`A5 5B 00 17 00 01 00`，尾部 `00 4A 45` 丢），解析器卡住 100 ms 后被
  半截帧看门狗复位（`stalls+1`）；
- 期间发生过**一次 UART 错误**（`rxerr=1`），HAL 遇错会 `UART_EndRxTransfer()` 中止本次接收，
  剩下的字节就再也进不来；`uart_rx_rearm` 把它救回来，所以重试能通。

**还没查明的部分**：`herr=0x00` —— HAL 在错误回调里 `ErrorCode` 已经是 0（HAL 内部的清标志时序），
抓不到错误类型；`loopmax=3767 µs` 说明主循环有过一次 3.7 ms 的阻塞（来源是"等心跳发完"那次
`APP_WaitTxDone`），但它不是每次都在第一帧那个时刻发生，两者因果关系未证实。

**结论与取舍**（用户 2026-11-05 决定）：
- 五项功能测试**照常做**，每条命令都会在重试那次成功，代价是每条多花一次超时；
- **唯一要避开的事**：不要用 `U1_DUT` 这版做固件上传/烧录（`0x0009/0x000A/0x000B`）。
  上传是连续数据流，首帧被截断会让整次上传失败 —— 烧录仍用 `U1_UART` 那版。

### 7.2 台架版心跳会占用一点带宽

`JIG_DUT_LINK=1` 的构建里，USART1 上电会打一行横幅，之后**链路安静 3 秒**就打一行心跳
（`[JIG] t=..s rx_bytes=.. frames=.. ...`）。收到第一帧后不再静默，但仍会继续报。
工具会跳过非协议文本，不影响使用；要看数据时可以留着，不想要就把 `APP_BENCH_ALIVE` 置 0 重编。

### 7.3 U2 缺席导致的两处能力退化

`0x000E / 0x000F` 的交叉校验块恒无对侧数据（`NO_PEER` 置 1、不判失败）；`0x0013` 直接回超时。
④ 编码器退化成"预期边沿数 vs 被测板自己数的"。这是 `JIG_U2_LINK=0` 的既定代价，不是 bug。
