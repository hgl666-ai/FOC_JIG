## 1. 背景

### 1.1 硬件与角色

| 角色 | 型号 | 说明 |
|---|---|---|
| 治具主控 U1 | STM32F103**C8T6**（64KB/20KB） | USB CDC 或 UART 接 PC；GD25Q128 存固件；位翻转 SWD 打目标 |
| 被测板 DUT | STM32F405**RGT6** | FOC 驱动板，1MB Flash |
| 接线 | 治具 PA13→DUT SWDIO、PA14→DUT SWCLK、GND↔GND | **不接 NRST**（`SWD_USE_NRST=0`） |

### 1.2 计时数据

- 位翻转速度：`SWD_DELAY_LOOPS = 128` → SWCLK 约 **50 kHz**
- 一次 `0x001E` 完整自检：**约 30 秒**（含 128 KB 擦除 1~1.5 s 和重连）

### 1.3 两种 PC 链路（务必分清）

| 模式 | Keil Target | 产物 hex | USB 是否初始化 |
|---|---|---|---|
| **USB CDC（生产）** | `U1` | `U1/MDK-ARM/U1/U1.hex` | ✅ 是 |
| **UART（临时测试）** | `U1_UART` | `U1/MDK-ARM/U1_UART/U1_UART.hex` | ❌ 完全不初始化 |

由 `jig_mode.h` 的 `JIG_PC_LINK` 控制（`0`=USB，`1`=UART）。UART 模式下 `MEAS_PRINT_ENABLE` 自动关闭（PA9 让给 PC 链路）。

> ⚠ **烧错 hex 是这一路的第一个坑**：UART 版烧上去，USB 永远不枚举（因为 USB 那套代码根本没编进固件），会被误判成"USB 硬件坏了"。

## 2. 九个真 bug（逐个拆解）

> 下面每条都给出"现象 → 怎么查出来的 → 根因 → 改法 → 证据"。
> 参考实现指 `INFO/SWD烧录参考的开源项目2/DAPProg-master`（下称 **DAPProg**），它是同类硬件上验证过的实现。

### bug 1：SWCLK 时钟相位整体是反的

**现象**：不管怎么调速度、换线序，目标一个 bit 都不回（ACK 恒 `0b111`，线上没人驱动）。

**怎么查出来**：把 DAPProg 的底层时序宏逐行抄出来对比（`src/DAP/SW_DP.c:40-58`）：

```c
#define SW_CLOCK_CYCLE()  PIN_SWCLK_CLR(); delay; PIN_SWCLK_SET(); delay
#define SW_WRITE_BIT(bit) PIN_SWDIO_OUT(bit); PIN_SWCLK_CLR(); delay; PIN_SWCLK_SET(); delay
#define SW_READ_BIT(bit)  PIN_SWCLK_CLR(); delay; bit = PIN_SWDIO_IN(); PIN_SWCLK_SET(); delay
```

**根因**：DAPProg 是"**SWCLK 空闲高电平，每个时钟拍是一个低脉冲**"；我们的实现是"空闲低电平，每个时钟拍是一个高脉冲"——**相位整体相反**。

**改法**（`U1/Core/Src/swd_phy.c`）：
- `phy_clk_cycle()`：`CLK 低 → 延时 → CLK 高 → 延时`
- `SWD_WriteBit()`：`放数据 → CLK 低 → 延时 → CLK 高 → 延时`
- `SWD_ReadBit()`：`CLK 低 → 延时 → 采样 → CLK 高 → 延时`
- `SWD_PhyInit()` 空闲态：**SWCLK 高、SWDIO 高**

**证据**：改完之后 `0x001E` 的 `mode=4`（连续连接尝试）第一次就抓到了正确的 IDCODE `2B A0 14 77`。

---

### bug 2：切换序列后多做了一次线复位

**现象**：即使相位改对，连接仍然失败（`04 01`，ACK=`0b111`）。

**怎么查出来**：对比 DAPProg 的连接序列（`src/SWD_host.c:702-729`）：

```c
tmp_in[0..7] = 0xFF;  SWJ_Sequence(51, tmp_in);   // ① 51 拍 SWDIO=1
tmp_in = {0x9E,0xE7};  SWJ_Sequence(16, tmp_in);   // ② 0xE79E LSB first
tmp_in[0] = 0x00;      SWJ_Sequence(8, tmp_in);   // ③ 8 拍 SWDIO=0  ← 关键
// ④ 直接读 IDCODE
```

**根因**：我们原来是 ①线复位 → ②`0xE79E` → **③又一次 56 拍线复位** → ④1 拍空闲 → 读 IDCODE。
参考实现在切换序列之后是 **8 拍 `0x00`**，不是再一次线复位。

**改法**（`U1/Core/Src/swd_dp.c` 的 `SWD_Connect`）：把第二次 `SWD_LineReset()` + `SWD_IdleClock()` 换成 `for (k=0;k<8;k++) SWD_WriteBit(0u);`

**证据**：与 bug 1 一起生效后，连接稳定成功。

---

### bug 3：读数据在上升沿采样

**现象**：即使包发出了，ACK 也读成非法值（曾读到 `0b101`，WAIT 应该是 `0b010`——正好是一位错位/反相）。

**根因**：ADIv5 §B4.1.1——目标**在上升沿驱动**数据，主机应在**下降沿之后（时钟低电平期间）**采样。原来的代码"刚拉高就采样"，采到的是上拉的空闲电平。

**改法**：`SWD_ReadBit()` 改成 DAPProg 的 `SW_READ_BIT` 形态（见 bug 1 的改法）。

**证据**：`mode=2` 速度扫描里，同一档速度改前只能偶尔读对 IDCODE，改后稳定。

---

### bug 4：写数据没有建立时间

**现象**：写事务（DP 写 CTRL/STAT、AP 写 TAR/DRW）失败，读事务正常。

**根因**：原 `SWD_WriteBit` 是"`放数据` → 立刻 `拉高时钟`"（`phy_clk_cycle` 的第一句就是 `CLK 高`），数据相对上升沿的建立时间只有几十纳秒。

**改法**：`放数据 → CLK 低 → 延时 → CLK 高 → 延时`（与 DAPProg `SW_WRITE_BIT` 一致）。

---

### bug 5：事务尾部多 1 拍、且把线留在低电平

**现象**：一笔事务成功后，**紧接着的下一笔**拿不到 ACK。

**根因**：原实现事务结束后补了 1 个空闲时钟，并把 SWDIO 留在低电平；DAPProg 的 SWD 配置是 `idle_cycles = 0`，事务结束直接 `PIN_SWDIO_OUT(1U)`（**驱动为高**）。

**改法**：
- `swd_config.h`：`SWD_TAIL_IDLE_CYCLES = 0`、`SWD_IDLE_LEVEL = 1`
- `swd_phy.c` 的 `swd_idle_tail()`：末尾补 `phy_dio_dir(1u); phy_dio_write(1u);`

---

### bug 6：每个包之前没有"拉低 + 1 拍空闲"

**现象**：`ACK = 0b111`（目标根本没理会这一包）。间歇出现，且重试同一笔无效。

**根因**：**DP 靠 Start 位（SWDIO 的 `0→1` 跳变）识别包边界**。上一笔写操作在线上留下的最后一个电平是**校验位**；如果校验位是 `1`，下一笔的 Start 位（也是 `1`）**没有跳变** → DP 认不出新包 → 不回 ACK。
连接序列末尾的 8 拍 `0x00` 恰好起到了这个作用，所以"第一笔"总能成功、"之后的每一笔"会随机失败。

**改法**：`SWD_IdleClock()` 改成**无条件**"驱动 SWDIO 低 + 打 1 拍"，并在 `SWD_Transfer()` 发请求头**之前**调用它。

> ⚠ **踩过的坑**：第一次改这条时，`SWD_IdleClock()` 里还留着 `for (i=0; i<SWD_TAIL_IDLE_CYCLES; i++)`，而 `SWD_TAIL_IDLE_CYCLES` 已被改成 0 → **编译成了空操作，改动等于没生效**，白测了一轮。诊断字节 `[8]=A5/B6` 的版本标记就是为了防止这种"以为烧了新固件其实没有"。

---

### bug 7：上电后没清 sticky（AP 永远 FAULT）

**现象**（这条最迷惑）：
- DP 访问一切正常（读 IDCODE、读写 CTRL/STAT 都行）
- **AP 访问全部失败**：AP IDR 读失败、AP CSW 读失败、AP 写返回 **FAULT (`0b100`)**
- `SWD_PowerUp()` 却报"成功"

**怎么查出来**：加了个"AP 探针"（读 AP 的 IDR/CSW 这类只读寄存器），结果 `[2]=FF`、`[7]=FF` —— **AP 整条通路不可访问**，而 DP 完全正常。

**根因**：AP 访问一旦返回 FAULT，会锁住 `STICKYERR`，之后**所有 AP 访问都返回 FAULT**，而 DP 访问不受影响。触发点通常是"上电刚过、AP 还没就绪"的第一笔 AP 访问。
DAPProg 在连接后**立刻写一次 DP ABORT 清所有 sticky**（`SWD_host.c:781`），我们只在"遇到 FAULT 时被动清"、且清完不验证。

**改法**：
- `swd_dp.c` 的 `SWD_PowerUp()`：上电成功后**立刻** `SWD_ClearSticky()`
- `swd_memap.c` 的 `SWD_MemInit()`：进 AP 之前再清一次

**证据**：改之后 `mode=5` 的现场读数为 `CTRL/STAT = 0xF0000000`（四个电源位全置位）且 **AP IDR 读返回 ACK OK**；`0x001E` 自检一路走到擦除阶段。

---

### bug 8：失步后只重试同一笔（无效）

**现象**：擦除阶段失败，`[15]=8B`（AP 写 TAR），`dp_xfer` 已经对 NO_ACK 重试了 8 次，**全部失败**。

**根因**：DP 已经失步（比如某一笔数据阶段被打断，DP 还在等 33 拍数据），**重试同一笔只会继续错**。只有线复位+切换序列（重新连接）才能恢复。

**改法**（`swd_selftest.c`）：擦除 / 写 / 校验任一阶段失败且是 NO_ACK 时，**回到 `SST_ST_CONNECT` 整条链重来**（连接→上电→MEM-AP→停机→冻结看门狗→继续），最多 6 次。

**证据**：加上之后，自检完成（30 秒内自动恢复若干次）。

---

### bug 9：速度太快（~1 MHz 已是误码边缘）

**现象**：同一固件、同一块板，IDCODE **有时读对、有时读错**（读到 `C4E80437`、`E1740037` 这类）。

**怎么查出来**：`0x001E` 的 `mode=2` 速度扫描（初版），实测：

| 延时循环 | SWCLK 约 | 结果 |
|---|---|---|
| 8 | ~1 MHz | ❌ 连上但 IDCODE **错位** |
| 32 | ~250 kHz | 时对时错 |
| **64 及以上** | ≤125 kHz | ✅ 全部正确 |

**改法**：`swd_config.h` 的 `SWD_DELAY_LOOPS` 默认值 **8 → 128**（约 50 kHz）。

**遗留**：50 kHz 烧 512 KB 会偏慢，后续可考虑"自适应测速"（上电试几档，选最快能稳定读对 IDCODE 的那档）——`SWD_PhySetDelay()` 已经支持运行期调速。

## 4. 诊断工具箱（`0x001E` 的 6 个模式）

> 这些是这次调试留下的"穷人逻辑分析仪"，**建议保留**。它们让"没有示波器也能定位"。

**命令**：`0x001E`，LEN=0（完整自检）或 LEN=1 + `DATA[0]=mode`
**应答**：固定 16 字节

| mode | 名称 | 帧（含 CRC） | 作用 |
|---|---|---|---|
| 0 | 完整自检 | `A5 5B 00 1E 00 01 00 00 4B 99` | 连接→擦→写→校验→读 UID |
| 1 | 引脚活动测试 | `A5 5B 00 1E 00 02 00 01 01 7E 4B` | 阶段1(0~2s) SWCLK 方波；阶段2(2~7s) 双线驱动低（供万用表量到目标端）；阶段3 抓 32 拍波形进 `[9..12]` |
| 2 | 速度扫描 | `A5 5B 00 1E 00 02 00 01 02 7F 0B` | 8 档延时（64…8192）各跑"连接+上电+MEM-AP"（**含写事务**），用 `0=全过 / 20=DP写失败 / 10=AP写失败 / 40=IDCODE错 / 8x=连接失败` 区分 |
| 3 | 波形捕捉 | `A5 5B 00 1E 00 02 00 01 03 BF CA` | 发 IDCODE 请求头后抓 24 拍进 `[1..4]` |
| 4 | 连续连接尝试 | `A5 5B 00 1E 00 02 00 01 04 7D 8B` | 5 秒内不停重连，验证"是否与复位时机有关" |
| 5 | DP/AP 探针 | `A5 5B 00 1E 00 02 00 01 05 BD 4A` | 打印 CTRL/STAT 原值、AP IDR、DP SELECT |

### 4.1 完整自检（`0x001E` LEN=0）应答字段

| off | 字段 | 说明 |
|---|---|---|
| 0 | `status` | `00` 全过 / `04` SWD失败 / `05` 回读不符 / `01` 忙 |
| 1 | `stage` | `01`连接 `02`擦除 `03`写 `04`校验 `05`读UID `FF`完成 |
| 2..3 | `bad_off` | 首个不符字节偏移；`FF FF` = 无不符 |
| 4..7 | `idcode` | 应为 `2B A0 14 77` |
| 8..9 | `dev_id` | 应为 `04 13` |
| 10..11 | `written` | 已写字节数 |
| **12** | `last_ack` | 失败时线路上的**原始 3 位 ACK**（`01`OK `02`WAIT `04`FAULT `07`/`05`=非法） |
| **13** | `last_err` | 内部错误码 = `(uint8_t)(-返回码)`（`01`=NO_ACK `02`=WAIT `03`=FAULT `08`=未停机） |
| **14** | `substep` | 失败子步骤：`1`连接 `2`上电 `3`MEM-AP `4`停机 `5`看门狗 `6`擦除 `7`写 `8`校验 |
| **15** | `last_req` | 最后一笔事务的**请求头字节**：`A5`DP读IDCODE / `A9`DP写CTRL/STAT / `8D`DP读CTRL/STAT / `B1`DP写SELECT / `A3`AP写CSW / `8B`AP写TAR / `BB`AP写DRW / `9F`AP读DRW / `BD`DP读RDBUFF |

**`[12][13][14][15]` 这四个字节是这次调试的核心武器**：它们能把"哪一步、哪一笔事务、目标回了什么"直接说出来，不必猜。

### 4.2 其它相关命令

| 命令 | 帧 | 作用 |
|---|---|---|
| `0x000C` 查槽状态 | `A5 5B 00 0C 00 01 00 00 48 21` | `06`=槽里没固件（**说明 SPI Flash 读通路正常**）；`03`=SPI Flash 读失败 |
| `0x001C` SPI Flash 诊断 | `A5 5B 00 1C 00 01 00 00 8B E0` | 64 字节：JEDEC ID、SPI2 寄存器快照、引脚配置、回读校验等（详见 `INFO/命令大全.txt` 第 23 条） |

## 5. 同期的其它修复（非 SWD，但同一天踩到）

| # | 问题 | 根因 | 处理 |
|---|---|---|---|
| A | C6T6 上 SPI2 **完全不可用**（`CR1/CR2=0`、写了不生效、`SR.TXE=0`） | 两颗不同的 C6T6 结果字节级一致 → 芯片/批次特性，**不是固件配置** | 换回 C8T6 后 SPI2 正常；C6T6 路线废弃（`U1_C6T6_32K` target 保留但已退役） |
| B | `0x000C` 曾回 **24 秒**才应答 | 2 槽 × 12 字节 × `HAL_SPI_TransmitReceive(..., 1000)` 超时 = 24 次 SPI 传输 | `GD25Q_SPI_TIMEOUT_MS` 1000 → **5 ms**，并让错误向上传播 |
| C | SPI Flash 读失败伪装成"槽里没固件"（`06`） | `GD25Q_ReadBuffer` 返回 void，读失败返回 0 被当成空槽 | 改成返回状态（1 成功/0 失败）；`Flash_ReadHead` 失败返回 2 → 上层回 **`03 ERR_FLASH`** |
| D | 潜在数据损坏：从坏 SPI 读到垃圾后照样"编程并校验通过"（零 vs 零） | 同上，读失败没检查 | 编程/校验/上传回读全部检查返回值 |
| E | 运行时调用 `HAL_SPI_Init()` 诊断导致**板子崩**（CS 掉到 0.4V，串口吐 `1F 1F 1F`） | `HAL_SPI_Init` 重入会重跑 `HAL_SPI_MspInit`，把 PB12 重置成 AF_PP | **已删除运行时重初始化，不要加回来**；诊断改为只读，收尾无条件 `GD25Q_Init()` |
| F | F4 扇区表只有 8 项（512KB），但 `F4_FLASH_SIZE` 是 1MB | `F4_EraseSector(11)` 返回 `SWD_ERR_PARAM` | 扇区表扩到 12 项（16×4 + 64 + 128×7）+ 编译期断言 |
| G | `0x000C` 早期应答把**栈垃圾**当版本号 | 提前返回路径没初始化响应缓冲 | `uint8_t resp[4] = {0, 0x00, 0xFF, 0xFF}` |

## 7. USB CDC 恢复测试指引

### 7.1 为什么现在是 UART

USB CDC 插上电脑**没有任何反应**（连"未知设备"都不弹）。为了不阻塞烧录功能验证，临时切到 UART（`JIG_PC_LINK=1`，Target `U1_UART`）。**这是临时措施，生产必须回到 USB CDC。**

### 7.2 恢复前必须先确认的三件事

| # | 检查 | 说明 |
|---|---|---|
| 1 | **烧的是 `U1.hex`（USB target），不是 `U1_UART.hex`** | UART 版**完全不初始化 USB**（`MX_USB_DEVICE_Init()` 被 `#if` 掉），烧它 USB 永远不枚举 |
| 2 | `U1` target 的 Define 里**没有** `JIG_PC_LINK=1` | 有的话就会被编成 UART 版 |
| 3 | BOOT0 = 0（复位后运行用户程序） | BOOT0=1 会停在 ST 串口 bootloader，什么都不会跑 |

### 7.3 固件侧已核实无误（不要重复怀疑）

| 环节 | 证据 |
|---|---|
| PA11/PA12 配成 AF 推挽 | `usbd_conf.c:76-77` |
| USB 时钟使能 | `__HAL_RCC_USB_CLK_ENABLE()` |
| USB 中断使能（优先级 0） | `USB_HP/LP_CAN1_*_IRQn` |
| `USBD_Init` → `RegisterClass(CDC)` → `USBD_Start` | `usb_device.c:71/75/83` |
| 中断入口编入固件 | `stm32f1xx_it.c`（`#if JIG_PC_LINK == USB` 内） |
| USB 48 MHz（72/1.5） | `RCC_USBCLKSOURCE_PLL_DIV1_5` |
| 原理图有 D+ 1.5k 上拉 + USBLC6-2E | `docs/01` 记录：R90 = 1.5k、USBLC6-2E |

### 7.4 关键判据：D+ 上有固定 1.5k 上拉

D+ 的上拉是**硬件固定**的，不受固件控制。所以：

> **哪怕 MCU 完全死掉，只要线插上、上拉存在，Windows 至少会报"无法识别的 USB 设备"。**
> 现在**完全没有弹窗** → 主机根本没看到上拉 → 问题在 D+ 这条通路或供电，**不在固件**。

### 7.5 待查清单（按命中率排序）

1. **换一根确定能传数据的 USB 线**（充电线没有 D+/D-，是"完全没弹窗"的头号原因）
2. **换 USB 口 / 换一台电脑**
3. **设备管理器 → 查看 → 显示隐藏的设备**，看有没有"未知 USB 设备（设备描述符请求失败）"
4. 万用表量 **PA12（D+）对 GND**（插着 USB）：
   - 期望 **≈3.0 V**（1.5k 上拉 + 主机 15k 下拉分压）
   - **≈0 V → 上拉失效**：查 R90 是否虚焊/掉落、R90 上端有没有 3.3 V、**USBLC6-2E 的 D+ 脚是否对地击穿**
5. 量 **PA11（D-）** ≈0 V；量 **PA11 与 PA12 之间不能短路**（换芯片时最容易连锡）
6. 量 **治具 GND ↔ USB 座外壳/地**
7. 确认治具 3.3 V 稳定（USB 供电时）

### 7.6 恢复步骤建议

1. 烧 `U1/MDK-ARM/U1/U1.hex`（Keil target `U1`）
2. 插 USB，看是否枚举
3. 枚举成功后，用 `python tools\foc_jig_tool.py -p COMx selftest` 复跑一遍 `0x001E` 自检 —— **确认 USB 链路上的 SWD 功能同样正常**（USB 与 UART 只影响 PC 链路，SWD 代码完全相同，但必须实测确认时序/缓冲没引入新问题）
4. 两边都通过后，把 `jig_mode.h` 的默认 `JIG_PC_LINK` 保持 `USB`（出厂态），`U1_UART` target 仅作调试用

## 8. 教训（写给未来的自己）

1. **仿真是理想线，不能替代硬件。** 这次 9 个 bug 全部在仿真里"通过"——因为仿真没有边沿延迟、没有飞线电容、不检查建立时间、模型是我按自己的理解写的。**推论：涉及电气时序的东西，仿真只能验证"逻辑对不对"，不能验证"能不能工作"。**

2. **参考实现要逐行对照，不要"按理解重写"。** 最终把 9 个 bug 找出来的方法，是把 DAPProg 的时序宏和连接序列**逐行抄出来对比**。之前所有"我觉得应该这样"的推理都错了方向。

3. **诊断信息要能自证。** `[12]`原始ACK / `[13]`错误码 / `[14]`子步骤 / `[15]`请求头，这四个字节把"猜"变成了"看"。而且要有**版本标记**（`[8]=A5/B6`），否则会出现"以为烧了新固件、其实改动没生效"（bug 6 的坑）。

4. **一次只改一个变量**，但也要敢于"整段照搬"。前者用于定位，后者用于收敛。

5. **"某个东西能用"不能替代"当前这个配置能用"。** 一度把"ST-Link 能读"当成"目标无条件下都能被读"，这个前提错了会带着整轮排查跑偏。

6. **被排除的假设要记下来**（第 3 章）。否则下次会从头再查一遍接线、地、供电。
